## 一、项目与职责

### 1. 项目的完整流程是什么？主要解决什么问题？

**参考回答：**

> BFI 是用户行为分析平台，解决海量网络流量数据接入后难以实时清洗、查询和形成用户画像的问题。还原机接收到报文后按规则解析成项目统一格式，再写入 Kafka；Flink 消费 Kafka 数据，完成清洗和业务处理，并按业务主题分发到不同 Doris 库表。系统基于这些基础数据继续形成布控、碰撞、关系分析和用户画像等业务数据。
>
> Doris 负责大规模明细和分析查询。画像任务由 Flink 从 Doris 读取数据并计算，再写入 Elasticsearch，为人物画像和 App 画像提供多字段组合检索。后端向业务人员提供用户查询、智能筛选、碰撞分析、布控任务和画像展示等能力。

主链路可以记成：

```text
还原机报文
  → 规则解析
  → Kafka
  → Flink 清洗与业务分发
  → Doris 基础/业务数据
  → Flink 画像计算
  → Elasticsearch 画像索引
  → 后端业务接口
```

### 2. 你在项目中担任什么角色？

**参考回答：**

> 团队一共 6 人，我主要负责后端开发，也会开发部分 Flink 任务。后端侧参与用户管理、数据处理、筛选分析、布控等业务能力；数据侧负责把部分业务规则落到 Flink 任务中，并配合 Doris 表设计和查询问题排查。
>
> 我不会把整个 Kafka、Flink、Doris 集群架构都说成由我独立设计。我的重点是业务后端、部分实时处理任务，以及大数据量下的查询实现。

### 3. 项目数据规模怎么描述？

**参考回答：**

> 原始数据每日约 20 亿条，每条原始记录有 8 个字段，保留半年。这里的 20 亿是记录数，不是字节数；TB 级指累计数据规模。没有准确的压缩后存储统计，所以不会在面试中换算具体 TB，也不会编造峰值 TPS。

## 二、Doris 与 Elasticsearch

### 4. Doris 在项目中起到什么作用？

**参考回答：**

> Doris 保存需要实时分析的基础数据和业务数据，承担按日期、IMSI、手机号、Host 和布控 ID 等条件的过滤、聚合和关联查询。相比 MySQL，它更适合大规模列式扫描、分区裁剪和并行聚合，也能通过分桶和二级索引优化高基数条件。

### 5. Doris 查询已经很快，为什么还需要 Elasticsearch？

**参考回答：**

> 两者解决的问题不同。Doris 是分析事实数据的主存储，适合按时间范围做过滤、聚合和统计；Elasticsearch 保存 Flink 计算后的用户及 App 画像，重点支持多字段检索。
>
> 画像查询会把输入按空格拆成多个条件，并支持 AND、OR、NOT 以及“不包含”等组合。ES 的倒排索引和布尔查询更适合这种检索体验。如果只是结构化等值和范围分析，优先使用 Doris；只有画像检索需要灵活组合条件时才走 ES。

### 6. Doris 和 ES 的数据如何保证一致？

**当前链路：**

> Flink 从 Doris 读取事实数据，计算画像后写入 ES。Doris 是事实来源，ES 是可重建的派生索引，因此两者采用最终一致性，而不是分布式强一致。

**建议回答：**

> ES 文档使用稳定的用户或 App 标识作为 `_id`，重复计算时执行 Upsert，避免生成重复画像；文档携带画像版本或更新时间，防止旧任务覆盖新结果。写入失败应记录失败批次并重试，无法恢复的数据进入失败记录。定时任务按数量、版本或抽样内容对账，发现差异后从 Doris 重新计算并覆盖 ES。
>
> Flink Checkpoint 只能恢复算子状态和读取位置，不能自动把 Doris 读取和 ES 写入变成一个分布式事务。因为 ES 是派生数据，所以允许短时间不一致，并以重算能力兜底。

只有稳定 ID、版本、重试和对账在真实代码中存在时，才能说“已经实现”；否则要说“为了完善一致性，我会这样设计”。

## 三、大数据量查询与表设计

### 7. 项目最大的难点是什么？

**参考回答：**

> 最大难点是数据接入后写得进去，但按业务条件无法在可接受时间内查询。原始数据每天约 20 亿条，业务查询通常还会叠加日期、IMSI、手机号、Host 或布控 ID；如果所有数据长期落在单张大表，查询和生命周期管理都很困难。
>
> 项目按访问范围做物理拆表：全量数据每周一表，布控数据每月一表；每张表内部再按天分区，用日期做分区裁剪。分桶优先选择高频、分布相对均匀的等值字段，例如 IMSI；手机号、Host 和布控 ID 根据等值、`IN` 或文本检索方式选择倒排索引或 BloomFilter。
>
> 这个设计减少了单次查询涉及的数据范围，也便于按周或按月清理历史表，但项目没有保留优化前后耗时和扫描行数，因此我只讲设计与取舍，不给出性能提升比例。

### 8. 为什么按周拆表后，还要按天分区？

**参考回答：**

> 周表负责控制单张物理表的生命周期和规模，大部分查询可以先路由到最近一张周表；日分区进一步让一两天的查询只扫描对应分区。查询超过一周时，需要由服务端确定目标表并组合结果。
>
> 代价是跨周查询要做多表 `UNION` 或分批汇总，Schema 变更、索引建设和清理任务也要覆盖多张表。如果查询经常跨越数周，单表按天分区可能更简单，因此这项设计最终仍应通过 Query Profile 和压测验证。

### 9. 全量数据为什么按周分表，布控数据为什么按月分表？

**参考回答：**

> 全量数据增长更快，每日约 20 亿条，因此采用更短的周级表控制单表规模；布控数据是经过业务规则筛选后的数据，数据范围和主要查询周期不同，所以使用月表。两类表都按天分区，以匹配常见时间条件。

这段回答成立的前提是布控数据量确实小于全量数据。如果面试官继续追问比例，只回答有记录的数据。

### 10. 分桶字段和索引怎么选择？

**参考回答：**

> 分桶字段优先选择高基数、分布均匀且经常用于等值过滤的字段。IMSI 是主要候选，但要先检查是否存在空值、默认值或少数热点 IMSI，否则会造成数据倾斜。
>
> 手机号、布控 ID 这类高基数等值查询可以评估 BloomFilter 或倒排索引；Host 如果是完整域名等值查询，可以使用倒排索引，如果是 `%keyword%` 模糊匹配，则要选择适合子串检索的索引。索引不是越多越好，它会增加写入、构建和存储成本，必须用 Query Profile 验证过滤行数。

### 11. 你说有 TB 级分库分表经验，具体是什么场景？

**严谨回答：**

> 更准确地说，我做的是 TB 级 Doris 大表组织和查询优化，不是传统 MySQL 分库分表。全量数据按周拆成物理表，布控数据按月拆表，表内按天分区，再按 IMSI 等字段分桶，并根据查询谓词建立二级索引。应用层根据时间范围路由目标表，跨周期查询组合多个表的结果。

**遇到的主要问题：**

- 跨周、跨月查询需要安全地拼接多个已知表名。
- 多张表的 Schema、索引和权限必须保持一致。
- 周表和月表到期后要可靠清理。
- 分桶键包含空值或热点值时会产生数据倾斜。
- 表、分区和 Bucket 过多会增加元数据与小文件压力。
- 新增索引会增加写入和存储成本，不能凭感觉全部创建。

**不要这样回答：**

> 我使用 ShardingSphere 把 Doris 做了分库分表。

项目没有该事实，而且 Doris 的 Partition、Bucket 与 MySQL Sharding 不是同一个概念。

### 12. 没有优化前后指标，怎么回答性能优化？

**参考回答：**

> 我可以解释当时的数据规模、查询条件和表设计，但因为没有保留优化前后的耗时、扫描行数和 Query Profile，所以不能给出提升百分比。这也是我的复盘点：以后优化前先固化典型 SQL、P95 耗时、扫描行数和资源消耗，改造后使用同一数据范围复测。

## 四、Flink 稳定性

### 13. Flink 如何处理重复数据？

**参考回答：**

> 项目上游按业务规则保证数据唯一性，Flink 仍不能假设故障恢复后绝对不会重放。Checkpoint 保存状态和 Kafka 消费位置；恢复时，Checkpoint 之后的数据可能再次消费。写 Doris 时还需要 Connector 的事务能力、唯一 Label、2PC 或目标表的幂等模型，才能把重复影响控制住。
>
> 因此不能只回答“上游保证唯一”或“开了 Checkpoint 就不会重复”。

### 14. 如何处理脏数据和乱序？

**参考回答：**

> 项目中无法反序列化或字段格式不符合约束的脏数据会被丢弃。更完整的做法是记录脏数据数量、来源和错误类型，并把必要样本写入隔离流，避免静默丢弃后无法对账。
>
> 脏数据与乱序是不同问题。只有业务使用事件时间窗口时，乱序才需要通过 Watermark、允许延迟和迟到数据策略处理；项目没有落地的机制不要补充成现状。

### 15. Checkpoint 失败后怎么恢复？

**参考回答：**

> 开启 Checkpoint 后，任务失败会按重启策略从最近成功的 Checkpoint 恢复算子状态和 Kafka 位置。还要监控 Checkpoint 时长、失败次数和存储可用性。恢复一致性最终仍取决于 Source 是否可重放以及 Sink 是否支持事务或幂等。

### 16. 出现反压时为什么不能只增加 JVM 堆内存？

**参考回答：**

> 反压说明下游处理速度低于上游输入速度，增加堆内存只能暂时容纳更多对象。应先在 Flink Web UI 找到最早出现 Busy 和 Backpressure 的算子，再检查数据倾斜、外部 Sink 变慢、窗口状态增长、序列化和网络 Buffer。
>
> 如果根因是热点 Key 或全量窗口，增加内存只会推迟 OOM；应修改 Key、使用增量聚合、限制状态生命周期或提高下游吞吐。

## 五、真实测试事故：Flink OOM

### 17. 讲一个 Flink 处理数据时发生 OOM 的案例

**参考回答：**

> 测试环境中有一个画像统计任务，早期版本没有直接丢弃空 IMSI，而是把空值统一转换成 `UNKNOWN`，然后按 IMSI `keyBy`，使用 10 分钟窗口和 `ProcessWindowFunction` 统一计算。
>
> 压测数据中空 IMSI 占比较高，所有 `UNKNOWN` 数据都进入同一个 Subtask。`ProcessWindowFunction` 在窗口触发前保存了该 Key 的全部记录，导致这个 Subtask 的堆持续增长。最开始看到的是下游反压和 Full GC，之后 TaskManager 抛出 `java.lang.OutOfMemoryError: Java heap space` 并重启。
>
> 排查时先在 Flink Web UI 对比各 Subtask 的 `numRecordsIn`、Busy 和 Backpressure，发现一个 Subtask 明显偏高；再查看 GC 和 Heap 指标，并通过堆转储确认窗口数据占用了主要内存。根因不是 JVM 参数太小，而是空 IMSI 形成热点 Key，加上全量窗口保存了所有事件。
>
> 修复分两部分：首先在 `keyBy` 前校验 IMSI，脏数据直接丢弃并计数，不再进入画像聚合；其次把全量 `ProcessWindowFunction` 改为增量 `AggregateFunction`，窗口内只保存统计值。调整并行度和堆内存只作为测试阶段止损，不作为根治方案。

### 18. 如何复现这个 OOM？

使用测试数据源持续生成记录，其中一部分 IMSI 为空，并保留下面的错误逻辑：

```java
stream
    .map(event -> {
        if (event.getImsi() == null || event.getImsi().isBlank()) {
            event.setImsi("UNKNOWN");
        }
        return event;
    })
    .keyBy(Event::getImsi)
    .window(TumblingProcessingTimeWindows.of(Time.minutes(10)))
    .process(new FullWindowProfileFunction());
```

复现步骤：

1. 使用较小的 TaskManager Heap 和有限并行度启动测试任务。
2. 持续生成数据，并让较高比例记录使用空 IMSI。
3. `FullWindowProfileFunction` 遍历整个窗口，不做增量聚合。
4. 观察某个 Subtask 的输入、Busy、Backpressure、Heap 和 Full GC。
5. 窗口状态持续增长后即可复现 OOM。

修复后的主逻辑：

```java
DataStream<Event> valid = stream
    .filter(event -> event.getImsi() != null && !event.getImsi().isBlank());

valid
    .keyBy(Event::getImsi)
    .window(TumblingProcessingTimeWindows.of(Time.minutes(10)))
    .aggregate(new IncrementalProfileAggregate());
```

::: warning 复现边界
复现时可以调整数据速率、空 IMSI 比例、窗口长度和 TaskManager Heap 加快出现问题，但不要把这些复现参数说成生产环境真实参数。
:::

## 六、架构选择

### 19. 项目为什么没有使用微服务架构？

**参考回答：**

> 团队只有 6 人，Web 业务 QPS 不高，少量实例通过 Nginx 负载均衡已经能够满足请求压力。系统的主要计算和存储压力在 Kafka、Flink、Doris 和 ES，这些组件本身可以独立扩容；把 Web 业务拆成多个微服务并不能解决数据处理瓶颈。
>
> 保持单体可以降低服务注册发现、链路追踪、分布式事务、接口治理和部署运维成本。代码内部仍按用户、布控、筛选、画像等业务模块划分边界，避免单体变成无结构代码。

### 20. 微服务适合什么场景？

**参考回答：**

> 当业务域边界稳定，不同模块需要独立发布、独立扩缩容或故障隔离，并且有多个团队分别负责时，微服务才有明确收益。例如画像检索流量远高于后台管理，并且需要独立团队频繁发布，就可以拆成独立服务。
>
> 拆分前还要具备自动化部署、监控告警、链路追踪、服务治理和数据边界，否则只是把本地调用改成不稳定的远程调用。

### 21. 单体如何保证可维护性和可用性？

**参考回答：**

> 可维护性靠模块边界，而不是进程数量。项目可以按用户、布控、画像、分析和基础设施分包，禁止模块绕过服务接口直接依赖内部实现。可用性上部署少量无状态实例，由 Nginx 负载均衡；实例故障时由其他实例承接请求。Kafka、Flink、Doris 和 ES 独立部署，不与 Web 应用共用进程资源。

## 七、复盘与补充追问

### 22. 如果重新设计 Doris 表，最先验证什么？

**参考回答：**

> 先收集最近一段时间的真实查询，统计时间范围、过滤字段组合和选择性；再比较周表加日分区与单表日分区的扫描行数、P95、跨周查询成本和元数据开销。分桶和索引使用 Query Profile 验证，而不是仅看 SQL 是否命中索引。

### 23. ES 故障会不会影响 Doris 主链路？

**参考回答：**

> ES 保存的是派生画像，Doris 是事实来源。ES 写入失败时不应阻塞原始数据进入 Doris；应记录失败批次并重试，画像查询可以提示数据更新时间。故障恢复后从 Doris 补算或重建 ES 索引。

### 24. 这个项目最大的收获是什么？

**参考回答：**

> 第一，大数据量系统不能只关注写入吞吐，表模型必须从真实查询模式反推。第二，Checkpoint、上游唯一性和 Sink 幂等是不同层次，不能用一个名词概括端到端一致性。第三，数据倾斜和状态模型往往比增加 JVM 内存更能决定 Flink 稳定性。最后，架构选择应匹配团队、流量和运维能力，微服务不是项目成熟度的标志。
