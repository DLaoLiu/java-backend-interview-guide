# 最新简历项目表达手册

> 主讲项目只保留三个：Chat-BFI、BFI 和通用日志平台。ServiceTag 用作大模型 API 追问补充，NFI 和油气田项目用于证明业务交付经验。

## 项目通用表达结构

按六句话组织，不要上来罗列技术栈：

1. **背景：** 谁遇到了什么问题。
2. **目标：** 系统要提供什么能力。
3. **职责：** 你负责哪些明确边界。
4. **难点：** 数据量、稳定性、一致性或业务复杂度。
5. **方案：** 为什么选择这些技术，关键流程是什么。
6. **结果与复盘：** 只说真实数据；没有数字就说能力和改进方向。

## Chat-BFI（第一主项目）

### 1 分钟版本

> Chat-BFI 是面向 BFI 业务数据的对话式分析 Agent，让业务人员通过自然语言完成趋势和明细查询，并识别重点关注对象。
>
> 我负责 FastAPI 接口和核心 Agent 流程，使用 LangChain 封装模型与工具，LangGraph 编排相关性判断、查询路由、Text2SQL、统计和结果返回；趋势与明细走不同分支。系统还区分当前上下文、历史会话和业务状态，通过 Checkpoint 支持恢复，在高风险或低置信度节点加入人工确认，并用 Langfuse 观测模型、Token、延迟和 Tool 链路。
>
> 这个项目的重点不是调用模型，而是把 SQL 安全、错误修复、状态管理和业务规则做成受控流程。

### 5 分钟必须展开

- 输入：问题、用户权限、会话状态。
- 路由：业务相关性、趋势或明细、是否需要澄清。
- 检索：Schema、字段、Join 和业务术语。
- 执行：SQL 生成、AST、白名单、只读、Limit、超时、脱敏。
- 分析：确定性统计和业务规则先计算，模型再解释。
- 治理：ReAct 重试上限、Human-in-the-Loop、Checkpoint、Langfuse。

## BFI 用户行为分析平台（第二主项目）

### 1 分钟版本

> BFI 面向网络流量和设备数据提供用户画像、智能筛选、碰撞分析和行为监控。数据来源包括实时流量、设备上报和 BCP 文件；实时数据通过 Kafka 接入，Flink 负责清洗、补字段和状态计算，Doris 保存明细及聚合数据，Elasticsearch 支持检索，Redis 缓存热点配置和结果。
>
> 我负责后端核心模块、实时数据处理相关能力和查询性能优化，重点处理多维筛选、数据分层、预计算以及大数据量下的查询响应。稳定性上关注 Kafka Lag、Flink Checkpoint 与反压、Doris 导入和幂等补偿。

### 5 分钟必须展开

- 数据源和业务实体是什么。
- 为什么 Kafka、Flink、Doris、ES 各自不可互相替代。
- 用户画像、碰撞分析如何转成查询或计算。
- 如何处理重复、乱序、任务失败和数据补偿。
- Doris 查询如何通过分区、分桶和预计算优化。

### 最可能追问

- TB 级数据量如何确认？日增量和保留周期是多少？
- Kafka 消息如何保证不丢和不重？
- Flink Exactly-once 是否覆盖到 Doris？
- Doris 为什么比 MySQL 合适？
- 做过哪一条真实的性能优化？

详细答案：[Flink、Doris 与 AI 工程](/bigdata-ai)、[分布式与性能](/distributed-performance)

## 通用日志监控平台（第三主项目）

### 1 分钟版本

> 多个业务系统都需要统一操作审计，复制日志代码会造成维护和口径不一致，所以我们把能力封装为 log-starter。业务方法使用自定义注解标记，AOP 切面采集用户、方法、参数摘要、耗时、结果和异常，再通过 Feign 或异步通道发送到日志服务。
>
> 我负责 Starter 架构、切面和日志发送客户端。设计上通过配置属性和条件装配降低接入成本，使用隔离线程池、超时和降级避免日志服务故障影响主业务；敏感参数需要脱敏，审计日志和普通日志使用不同可靠性策略。

### 5 分钟必须展开

- 自定义注解定义哪些元数据。
- AOP 使用 JDK 还是 CGLIB 代理，自调用有什么问题。
- 自动配置如何根据类路径和配置创建 Bean。
- 用户、requestId 等上下文如何获取和跨线程传递。
- 异步队列满、远程调用失败、日志服务不可用时怎么办。

### 最可能追问

- Starter 最少需要哪些组件？
- 为什么不用业务代码手动记录日志？
- 切面异常会不会影响主业务？
- 日志异步后丢失怎么办？
- 如何避免记录密码、身份证等敏感数据？

详细答案：[Spring、MyBatis 与微服务](/framework)

## ServiceTag（加分项目）

### 1 分钟版本

> ServiceTag 统一管理 App、小程序和 Web 服务的标签体系。我负责核心后端和大模型 API 集成，将服务信息和候选标签组成结构化 Prompt，要求模型按固定 Schema 返回建议；服务端执行候选范围和业务规则校验，低置信度或冲突结果进入人工审核。接口侧通过超时、限流、有限重试、缓存和降级保证稳定，人工修改用于后续评测和规则优化。

### 只准备这些追问

- 结构化输出失败怎么办？
- 如何评估标签准确率？
- 人工审核如何反哺？
- 如何控制 Token 和成本？
- 为什么不让模型结果直接入库？

## 项目真实性检查

面试前为每个项目写清以下信息，无法确认的不要说具体数字：

- 实际团队人数、你的职责边界。
- 数据来源、日增量、保留周期。
- 真实使用的组件和版本。
- 你亲自解决的一次问题。
- 优化前后的可验证指标。
- 哪些是已经上线，哪些只是后续设计。
