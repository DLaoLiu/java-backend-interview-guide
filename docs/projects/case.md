# 相似项目案例

## 案例名称

实时用户行为洞察与智能服务打标平台

这个案例把你简历里的“用户行为分析平台”和“多端服务打标管理平台”合并成一个更容易讲清楚的面试案例。它不是照搬简历，而是用于训练表达。

## 业务背景

公司有 App、小程序、Web 等多端服务，也有大量用户访问行为数据。运营和风控团队希望做到三件事：

1. 快速查询用户画像和行为轨迹。
2. 按标签圈选目标用户，做交叉分析。
3. 自动给服务打标签，降低人工维护成本。

## 你的职责可以这样讲

> 我主要负责后端核心模块和数据链路设计，包括用户画像查询、标签圈选、布控任务管理、服务打标和部分性能优化。架构上用 Spring Boot / Spring Cloud 拆分业务服务，用 Kafka 承接实时数据，用 Flink 做清洗和基础表构建，用 Doris 支撑多维分析查询，用 Redis 缓存热点配置和标签字典。

## 核心设计点

### 1. 用户画像查询

- 按 IMSI、IMEI、手机号等标识查询用户基础信息。
- 高频字段进入画像宽表，减少多表 join。
- 热点用户和标签字典用 Redis 缓存。
- 敏感数据查询接入权限控制和操作审计。

### 2. 标签圈选和碰撞分析

- 标签分为基础属性、行为偏好、风险特征、服务分类。
- 圈选条件先转换成查询计划，再走 Doris 分区和索引。
- 大范围查询通过预聚合表或异步任务输出结果。
- 结果集做权限隔离，避免越权查看。

### 3. 大模型服务打标

- 输入：服务名称、描述、所属端、已有分类、候选标签。
- 输出：固定 JSON，包含标签、理由、置信度。
- 规则校验：标签必须来自标签库，置信度低进入人工审核。
- 稳定性：超时、重试、限流、熔断、调用日志。

### 4. 性能优化

- MySQL 负责事务型配置和管理数据。
- Doris 负责大数据量分析查询。
- Elasticsearch 负责关键词检索。
- Redis 负责热点配置和短期结果缓存。
- 慢查询通过执行计划、分区裁剪、预计算和分页优化处理。

## 面试官追问与回答方向

| 追问 | 回答方向 |
| --- | --- |
| 为什么不用 MySQL 直接查？ | MySQL 适合事务型数据，TB 级多维分析会有扫描和 join 压力；Doris 更适合 OLAP。 |
| Kafka 消息重复怎么办？ | 下游按业务唯一键幂等，Doris/ES 写入也要设计可覆盖或去重逻辑。 |
| Flink 任务失败怎么办？ | 开启 Checkpoint，失败后从状态恢复；对外部 Sink 结合幂等保证结果一致。 |
| 标签打错怎么办？ | 自动推荐只做初筛，低置信度进入人工审核，审核结果回写样例库。 |
| Redis 缓存不一致怎么办？ | 配置类数据更新后删除缓存，热点数据设置过期时间，必要时用消息通知刷新。 |
| 大模型接口慢怎么办？ | 异步打标、批量处理、超时控制、重试退避、降级为规则打标。 |

## 可量化结果示例

如果真实项目没有准确数字，不要乱编。可以用保守表述：

- 将高频画像查询从多表实时 join 调整为画像宽表查询，响应更稳定。
- 标签字典和权限数据缓存后，后台管理接口的数据库压力明显下降。
- 大模型自动打标减少人工初筛工作量，人工主要处理低置信度结果。
- 通过预计算和分区设计，复杂圈选任务从同步查询改为异步任务，降低接口超时。

## 1 分钟讲项目模板

> 这个项目是一个实时用户行为洞察和服务打标平台，主要服务运营和风控场景。数据侧通过 Kafka 接入实时行为数据，用 Flink 做清洗和基础表构建，分析数据进入 Doris，检索数据进入 Elasticsearch，热点配置进 Redis。业务侧用 Spring Cloud 拆分用户画像、标签圈选、布控任务和服务打标等服务。我负责核心后端模块和部分性能优化，重点处理了多条件圈选查询慢、标签字典频繁访问、大模型打标结果不稳定等问题。最终方案是用预计算表、缓存、异步任务和人工审核兜底来保证查询性能和结果可靠性。
