# Chat-BFI 项目面试问答

## 项目事实卡

| 项目项 | 真实情况 |
| --- | --- |
| 项目状态 | 公司内部项目，因部门变动和整条业务线取消而未上线 |
| 团队规模 | 一名前端、一名后端 |
| 个人职责 | 后端开发，负责 FastAPI 接口和 Agent 核心流程 |
| 查询数据源 | Doris |
| 核心框架 | LangChain、LangGraph、Langfuse |
| 人工确认 | 任务计划生成之后 |
| SQL 校验现状 | 语法校验；趋势/明细特征校验 |
| 状态持久化 | PostgreSQL 保存 LangGraph Checkpoint，State 中包含历史消息 |
| 中间步骤 | 每步一条 SQL，创建带过期登记的 Doris 逻辑 View，后续步骤可引用 |

::: warning 表达边界
这个项目没有上线。回答时可以讲设计、开发和测试过程，不能说“上线后提升了多少效率”“线上故障影响了多少用户”。尚未实现的安全能力必须放在演进方案中。
:::

## 一、核心问题

### 1. 能介绍一下 Chat-BFI 的 LangGraph 流程吗？

**参考回答：**

> 整个流程是代码预先编排的有状态图。请求进入后，先由意图节点判断问题是否属于 BFI 业务；无关问题直接返回友好提示，相关问题进入输入规范化。之后召回相关业务表和字段，并使用 `BAAI/bge-reranker-v2-m3` 对候选 Schema 重排。
>
> 下一步由模型生成固定 JSON 结构的任务计划，服务端校验结构后进入人工确认。用户同意就开始执行；不同意时可以补充信息，再回到计划节点重新生成。
>
> 计划中的每个步骤只生成一条 SQL。循环内依次执行 SQL 生成、语法校验、趋势或明细特征校验和 Doris 查询。执行失败时，把标准化错误带回 SQL 生成节点，最多重试三次。步骤执行完成后创建一个逻辑 View，把 View 名称写入 State，后续步骤可以引用。所有步骤完成后，模型结合原问题和步骤结果生成总结。

可以把主链路记成：

```text
相关性判断
  → 输入规范化
  → Schema 召回与重排
  → 结构化任务规划
  → 人工确认
  → 按步骤循环（SQL 生成 → 校验 → 执行 → View 引用）
  → 结果总结
```

### 2. 为什么使用 LangGraph，没有只用 LangChain？

**参考回答：**

> LangChain 和 LangGraph 不是二选一。LangChain 主要负责模型调用、Prompt、结构化输出和 Tool 封装；LangGraph 负责把这些能力组织成带状态的流程。
>
> Chat-BFI 包含任务计划确认、拒绝后重新规划、多步骤依赖、SQL 失败重试以及中断恢复，不是单向 Chain。LangGraph 的 State、条件边和 Checkpoint 更适合显式表达这些路径，也方便定位某一步输入和输出。节点内部仍然使用 LangChain，所以准确说法是“LangChain 做能力封装，LangGraph 做工作流编排”。

### 3. State 是怎么设计的？

**参考回答：**

> State 围绕一次分析任务设计，主要保存会话标识、历史消息、当前 Message、规范化问题、召回的表结构元数据、任务计划、当前步骤、上一步生成的 View 名称、SQL、执行错误和重试次数。大结果不直接塞进 State，而是通过 Doris View 名称传递。
>
> Checkpoint 使用 PostgreSQL 持久化，历史消息当前也随 State 一起保存。这样可以支持人工确认和服务重启后的流程恢复，但它把工作流恢复数据与产品会话数据放在了一起，是当前实现的一个限制。

**推荐字段示意：**

```python
class AgentState(TypedDict):
    thread_id: str
    messages: list
    current_message: str
    normalized_question: str
    schema_metadata: list
    plan: list
    plan_status: str
    current_step: int
    step_view_names: list[str]
    current_sql: str | None
    query_type: str | None
    retry_count: int
    last_error: str | None
    final_answer: str | None
```

这只是面试中的字段归类，不代表项目使用了完全相同的类定义。

### 4. 连续三次 SQL 执行失败后怎么处理？

**参考回答：**

> 三次失败后不再让模型继续尝试，避免相同 SQL 循环消耗 Token 和 Doris 资源。系统将当前步骤标记为失败，保存原问题、任务计划、尝试过的 SQL、SQL 指纹和标准化错误。
>
> 如果前置步骤已有有效结果，就在最终回复中说明哪些步骤完成、哪个步骤失败，不基于残缺数据给出确定性结论；如果核心步骤失败，则返回可理解的失败原因并建议缩小范围或转人工处理。该案例同时进入后续回归样例。

**演进方案：**

- 区分语法错误、字段错误、权限错误、超时和资源不足。
- 相同 SQL 指纹或相同错误连续出现时提前终止。
- 只有可修复错误才重新生成 SQL；安全拒绝和权限错误不得重试绕过。

### 5. 任务计划为什么需要人工确认？

**参考回答：**

> 一次自然语言问题可能被拆成多个有依赖的查询步骤。如果计划一开始理解错了指标、时间范围或分析路径，后面的 SQL 即使都能执行，结果仍然没有意义。因此项目把人工确认放在执行前：用户可以看到结构化计划，同意后执行；不同意时补充信息并重新规划。
>
> 人工确认控制的是“分析路径是否符合意图”，不能替代 SQL 安全校验。

## 二、上下文与自动化边界

### 6. 项目怎么规避上下文混乱？

**参考回答：**

> 我理解的上下文混乱主要有两类：一类是上一轮历史影响当前新问题，另一类是当前轮任务还没执行完，用户又输入了一个新问题。项目里不会直接把所有历史消息拼进 Prompt 后让模型自由判断，而是以“当前输入”为主重新走输入规范化、意图判断和 Schema 召回。
>
> 如果当前会话存在未完成的分析任务，需要先根据新输入判断它是对当前任务的补充、取消/重做，还是一个新的分析问题。只有被判断为补充的信息，才合并进当前计划并重新规划；如果是新问题，就应该创建新的任务上下文，避免沿用上一轮的 Schema、SQL、View 名称和筛选条件。
>
> 已实现部分主要是：当前 Message、计划、当前步骤、View 名称、重试次数这些执行状态都放在结构化 State 里，多步骤之间传递 View 名称，而不是让模型从历史回答中猜前一步结果；计划执行前还有人工确认，可以提前纠正问题理解。当前不足是历史消息仍保存在 Checkpoint State 中，历史压缩、独立会话表、未完成任务的取消/分叉策略还没有完全产品化。如果继续建设，我会加 `task_id/run_id`、任务状态、最近消息窗口、滚动摘要和乐观版本号，明确控制“继承哪些上下文、不继承哪些上下文”。

### 7. 流程是全自动，还是由模型自己决定如何执行？

**参考回答：**

> Graph 的节点顺序、循环上限和人工中断点由代码固定。模型负责相关性判断、任务规划、SQL 生成、趋势或明细分类以及最终总结；Schema 召回、结构校验、循环次数和执行动作由代码控制。
>
> 因此它属于受约束的工作流型 Agent，不是让模型自由选择任意 Tool 的全自动 Agent。

### 8. 项目使用了 ReAct 吗？

**参考回答：**

> 按当前实现不能称为 ReAct。趋势或明细校验 Tool 是固定调用，具体检查有没有时间粒度和聚合函数，并不是模型根据 Observation 自主选择下一项 Action。项目有错误反馈和循环，但循环路径由 Graph 固定。
>
> 如果要实现 ReAct，需要让模型在受限 Tool 集中根据 Observation 选择下一步，同时仍由代码控制权限、最大迭代次数和终止条件。当前项目没有必要为了使用名词而增加这种自由度。

## 三、趋势、明细与 SQL

### 9. 怎么区分趋势查询和明细查询？

**参考回答：**

> 先由模型根据问题输出趋势或明细分类，再由固定校验逻辑检查 SQL 特征。趋势查询通常需要时间粒度和聚合函数；明细查询关注具体记录，不应被错误聚合。模型负责语义分类，代码负责检查生成 SQL 是否符合该分类。

**分类错误处理：**

1. 模型输出固定枚举和分类理由。
2. 校验 SQL 是否具有对应特征。
3. 分类与 SQL 不一致时，将差异反馈给 SQL 生成节点。
4. 连续不一致或问题同时包含趋势和明细时，回到计划节点拆成两个步骤。
5. 仍无法确定时向用户澄清，不猜测业务口径。

### 10. 怎么保证生成的 SQL 完全没有问题？

**参考回答：**

> 不能保证。当前项目做了 SQL 语法校验，以及趋势查询是否包含时间粒度和聚合函数的特征检查。这能拦住一部分错误，但不能证明字段权限、Join 关系、查询成本和业务口径完全正确。
>
> Text2SQL 必须区分“语法正确”“能够执行”和“业务结果正确”。项目当前只覆盖了前两层的一部分，所以面试中不能回答已经通过 Prompt 保证 SQL 完全正确。

**未实现的演进方案：**

- 使用 AST 只允许受控查询类型，并检查表字段白名单。
- 使用只读账号和最小权限访问 Doris。
- 明细查询强制行数上限，并限制时间范围。
- 设置查询超时，复杂查询执行前检查 `EXPLAIN`。
- 维护可信 Join 和指标口径，使用真实问题构建回归集。
- 对结果为空、行数异常和聚合值异常增加结果守卫。

### 11. SQL 执行成功，为什么结果仍可能错误？

**参考回答：**

> SQL 可能使用了错误时间字段、错误聚合粒度，或者一对多 Join 后把记录数当人数。数据库只能证明语法和执行成立，无法知道业务人员说的“人数”是否应该按 IMSI 去重。
>
> 因此模型生成后还要检查问题、计划、SQL 和结果口径是否一致。高频指标应沉淀为确定的业务定义，而不是每次让模型猜。

### 12. 遇到慢 SQL 怎么处理？仅通过提示词限制吗？

**参考回答：**

> 不能只依赖提示词。布控数据每天新增接近 5 亿条，通常查询最近一周，并以日期配合 IMSI、手机号、Host 或布控 ID 做过滤。当前布控数据按月拆表、表内按天分区，目的是先通过表路由和分区裁剪缩小扫描范围；再根据真实谓词为高基数等值字段选择倒排索引或 BloomFilter。
>
> 分桶键应选择最常见且分布均匀的等值查询字段，不能把所有查询字段都当成分桶键。手机号、Host 和布控 ID 更适合根据 `=`、`IN`、全文或模糊匹配方式选择二级索引。
>
> 项目没有保存优化前后耗时，也没有完成 `EXPLAIN` 或压测，所以只能说明表设计思路，不能声称性能提高了多少。

**进一步排查顺序：**

1. 确认 SQL 是否命中正确月表和日期分区。
2. 查看谓词是否能够下推、索引是否生效。
3. 检查扫描行数、返回行数、排序、聚合和 Join。
4. 缩小时间范围或把固定统计做成预聚合。
5. 设置资源上限，避免 Agent 慢 SQL 影响其他查询。

## 四、中间 View

### 13. 为什么每一步使用 View？它是不是临时表？

**参考回答：**

> 每个计划步骤只生成一条 SQL。为了让后续步骤引用前一步结果，项目创建带任务标识的 Doris View，把 View 名称写入 State，并在业务登记表中保存过期时间。定时任务每天扫描过期记录并执行 `DROP VIEW`。
>
> 它不是 Doris 临时表，也不是物化结果。普通 View 只保存查询定义，查询时仍会展开底层 SQL。优点是步骤之间通过稳定名称解耦；缺点是多层 View 会形成复杂嵌套查询，并且需要处理命名冲突、权限和过期清理。

### 14. View 过期清理怎么保证可靠？

**建议回答：**

> 创建 View 和写入过期登记应使用统一任务 ID。清理任务查询已过期记录，执行幂等的 `DROP VIEW IF EXISTS`，成功后更新清理状态；失败则记录原因并重试。创建流程异常时也要登记孤儿 View，避免只创建 View 却没有生命周期记录。

这部分只有在代码确实这样实现时才能使用“我们做了”；否则表达为改进方案。

## 五、难点、错误与收获

### 15. 项目中最大的难点是什么？

**参考回答：**

> 最大难点不是让模型生成一条能执行的 SQL，而是让多步骤查询保持同一业务口径。一个问题会先做 Schema 召回，再拆成多个依赖步骤；前一步理解或结果错误，会通过 View 继续影响后面的步骤。
>
> 我的处理方式是把计划结构固定为 JSON，服务端先校验，再由用户确认；每步只生成一条 SQL，把步骤、View 和重试信息写入 State。这样可以知道错误发生在问题理解、计划、SQL 还是执行阶段，而不是把整个过程放进一个 Prompt。

### 16. 在项目中犯过什么错？怎么弥补？

**参考回答：**

> 开发初期，我把 SQL 语法校验通过看成 SQL 正确。测试时模型生成了一条能够执行的聚合 SQL，但时间粒度与问题不一致，数据库正常返回了结果，业务含义却是错的。
>
> 发现后，我把校验拆成语法校验和查询类型校验：趋势查询检查时间粒度和聚合函数，明细查询避免错误聚合；分类与 SQL 特征不一致时重新生成。同时我也认识到这个修复仍不完整，后续还需要 AST 白名单、可信 Join、只读账号、查询超时和结果级评测。
>
> 这次错误让我意识到，Text2SQL 的执行成功率不等于业务正确率，Prompt 也不能替代确定性的工程校验。

### 17. 这个项目有什么收获？

**参考回答：**

> 第一，LangChain 和 LangGraph 的价值不在框架名，而在于把模型能力和工作流控制分开。第二，模型适合理解意图和生成候选方案，权限、重试上限和终止条件必须由代码控制。第三，Text2SQL 的核心指标应该是业务结果正确率，而不是 SQL 执行成功率。最后，未上线项目也要明确现状和演进方案，不能把目标架构说成已落地能力。

## 六、补充追问

### 18. 项目为什么没上线？

**参考回答：**

> 项目在公司内部开发阶段，后来因为部门变动和整条业务线取消而停止，不是因为某个技术问题导致上线失败。因此我会重点讲已经完成的流程、测试中发现的问题和未完成的工程项，不虚构上线效果。

### 19. Langfuse 在项目里做什么？

**参考回答：**

> Langfuse 用于记录一次 Agent 请求经过的模型调用和节点链路，关注 Prompt 版本、输入输出摘要、Token、耗时和错误。它能帮助区分延迟来自 Schema 召回、模型、SQL 执行还是重试。敏感 Schema、SQL 结果和个人数据需要脱敏或关闭采集，不能为了可观测性扩大数据风险。

### 20. 如果重新设计，优先改什么？

**参考回答：**

> 第一优先级是补齐 SQL AST、权限、超时和结果正确性评测；第二是把产品会话记录与工作流 Checkpoint 分开，增加最近窗口和历史摘要；第三是治理多层 View 的复杂度，对需要重复使用的大结果改为有生命周期的物化中间结果；最后才考虑让模型拥有更多自主 Tool 选择。
