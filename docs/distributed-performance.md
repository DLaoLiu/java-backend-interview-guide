# 分布式、Kafka、性能与高可用

> 这部分要从“技术名词”切换到“故障会发生时系统怎么办”。回答任何治理题都优先覆盖超时、幂等、限流、隔离、降级、监控和补偿。

## 分布式基础

### 1. CAP 和 BASE 怎么理解？

**回答：** 网络分区发生时，分布式系统通常必须在一致性和可用性之间取舍，因此 CAP 不是平时随意三选二。BASE 是工程上的折中：允许部分能力降级或短暂软状态，通过重试和补偿最终达到一致。选择取决于业务，例如余额扣减更重一致性，统计报表通常可以接受延迟。

### 2. RPC 和本地调用有什么区别？

**回答：** RPC 表面像调用方法，实际经过序列化、网络、服务发现、负载均衡和反序列化，可能出现超时、重复、部分失败和版本不兼容。调用方必须设置 Deadline、错误分类和重试边界，服务端要幂等、限流并提供链路标识。

### 3. Redis 分布式锁有哪些风险？

**回答：** 风险包括锁过期后任务仍在执行、客户端误删他人锁、主从切换导致锁丢失、续期线程暂停，以及锁粒度过大。实现时使用唯一 value、Lua 原子释放、合理租期和受控续期；真正的业务唯一性仍由数据库约束或状态机兜底。

### 4. 分布式事务有哪些方案？

**回答：** 2PC 一致性强但阻塞和协调成本高；TCC 由业务实现 Try、Confirm、Cancel，控制强但侵入大；Saga 适合长事务，通过一系列本地事务和补偿动作完成；可靠消息适合异步最终一致。选择时看一致性等级、业务可补偿性、吞吐和实现成本。

**项目表达：** 不要把普通数据库事务说成分布式事务。没有实际使用 Seata/TCC 时，可以说明项目采用本地事务加消息补偿或“设计上会如何选择”。

### 5. 如何设计分布式任务的幂等？

**回答：** 为每个业务任务生成稳定唯一键，在数据库通过唯一约束或状态机保证同一任务只生效一次；处理前检查状态，处理结果和状态变更尽量在同一事务内。失败重跑时区分“未执行、执行中、已成功、结果未知”，不能看到超时就直接重复。

## 消息队列 / Kafka

### 6. 为什么使用消息队列？

**回答：** 核心价值是异步、解耦、削峰和广播。例如 BFI 用 Kafka 承接持续到来的流量数据，让采集端和 Flink 处理端按各自节奏工作。代价是引入重复、顺序、积压、一致性和运维复杂度，所以低流量同步调用不一定需要 MQ。

### 7. Kafka 为什么吞吐高？

**回答：** Kafka 采用顺序追加日志、批量发送、页缓存和零拷贝等方式减少随机 I/O 和系统调用；分区允许并行读写。吞吐还受消息大小、批次、压缩、副本、确认级别、分区数和磁盘网络影响，不能只靠增加分区。

### 8. Kafka 如何尽量保证消息不丢？

**回答：** 生产端使用合适的 `acks`，开启重试并处理发送结果；Broker 配置足够副本和最小同步副本，避免不安全选主；消费者处理成功后再提交 offset，失败进入重试或补偿。所谓“不丢”必须明确故障范围和端到端边界，业务结果还需要幂等和对账。

### 9. Kafka 为什么会重复消费？如何处理？

**回答：** 消费者处理完成但 offset 尚未提交就宕机，恢复后会再次读取；生产端重试也可能产生重复。消费者通过业务唯一键、数据库唯一约束、幂等状态机或去重表保证重复执行结果一致。不能简单依赖内存 Set 去重，因为重启和多实例下无效。

### 10. Kafka 如何保证顺序？

**回答：** Kafka 只保证单分区内顺序。需要同一用户或任务的事件有序时，用稳定业务 key 将它们发送到同一分区，并在分区内串行处理。全局顺序通常意味着单分区，会牺牲吞吐；乱序可由版本号、事件时间或状态机处理。

### 11. Consumer Group 和分区有什么关系？

**回答：** 同一个消费组内，一个分区同一时刻只会分配给一个消费者，因此有效并行度不超过分区数；消费者多于分区时会有实例空闲。不同消费组可以独立读取同一主题，实现多个业务订阅。

### 12. Kafka Rebalance 有什么影响？

**回答：** 消费者加入、退出或分区变化会触发重新分配，期间可能暂停消费，并增加重复处理风险。要避免处理时间超过心跳或轮询配置，合理控制批次；使用增量协作式分配和静态成员可减少不必要迁移。消费者关闭时应优雅提交和释放资源。

### 13. 消息积压怎么处理？

**回答：** 先确认生产速率、消费速率、Lag 和下游耗时，判断是突发流量、消费者故障、慢 SQL 还是分区热点。短期可限流生产、扩容消费者到分区上限、批量处理或临时增加旁路消费；长期优化下游、调整分区和容量。扩分区会影响基于 key 的历史顺序，不能随意操作。

## 高性能与高可用

### 14. 限流、熔断、降级分别解决什么问题？

**回答：** 限流控制进入系统的流量，保护容量；熔断在依赖持续失败时快速失败，避免线程和连接被占满；降级主动关闭非核心能力或返回兜底结果，保证核心链路。三者通常配合使用，并通过监控决定阈值和恢复。

### 15. 常见限流算法有哪些？

**回答：** 固定窗口简单但边界可能突刺；滑动窗口更平滑但状态更多；漏桶以稳定速率流出，适合整形；令牌桶按速率发放令牌并允许一定突发，应用最广。分布式限流常用 Redis + Lua 或网关组件，但要考虑 Redis 故障时是放行还是拒绝。

### 16. 超时和重试应该如何设计？

**回答：** 超时应从用户请求的整体 Deadline 向下游分配，连接、读取和执行分别设限；下游超时必须短于上游，否则会出现无效工作。只对瞬时错误和幂等操作做有限次数、指数退避加抖动的重试，并设置重试预算，避免重试风暴。

### 17. 什么是服务雪崩？如何防止？

**回答：** 一个依赖变慢后占满上游线程、连接和队列，故障沿调用链扩散，就是雪崩。防护包括超时、舱壁隔离、有界队列、限流、熔断、降级、缓存和容量预估；监控要关注饱和度，而不只是错误率。

### 18. 如何实现接口性能优化？

**回答：**

> 我先用监控和 Trace 拆出网络、应用、缓存和数据库耗时，确认瓶颈后再优化。常见手段包括减少调用次数、并行独立 I/O、缓存热点、批量查询、避免 N+1、优化索引和分页、预计算，以及将分析查询迁到 Doris。优化后要比较 P95/P99、吞吐和资源占用，同时确认结果一致。

### 19. 日志服务挂了，如何不影响主业务？

**回答：** 日志采集切面只做轻量封装，发送使用隔离线程池或消息队列；调用设置很短超时，失败快速降级到本地缓冲或补偿队列。队列必须有界并监控丢弃量，审计类日志与普通操作日志按可靠性等级区分，不能统一“失败就丢”。

### 20. 如何设计灰度发布和快速回滚？

**回答：** 镜像和配置都使用不可变版本，通过用户、租户或流量比例逐步放量，比较错误率、延迟和关键业务指标。新版本异常时停止放量并回滚流量；数据库变更使用向前兼容的 expand-contract 方式，避免代码回滚后无法读取新结构。

### 21. 如何定义系统高可用？

**回答：** 高可用要用 SLA/SLO 和可测量指标表达，例如成功率、P95 延迟、恢复时间和数据恢复点。技术上通过冗余、故障检测、自动切换、限流降级、备份恢复和演练实现。只有多实例但共享单点数据库，不能称为完整高可用。

## BFI 项目一条线讲清

> 数据从设备或文件进入接入层，实时流量由 Kafka 削峰解耦，Flink 完成清洗、补充字段和状态计算，明细与聚合结果写入 Doris，检索字段进入 Elasticsearch，热点配置和查询结果进入 Redis。稳定性上关注 Kafka Lag、Flink Checkpoint 和反压、Doris 导入及查询耗时；一致性通过业务唯一键、Checkpoint、幂等写入和补偿任务共同保证。

只有真实使用过的部分才能说“我们这样做了”；其余改成“如果继续完善，我会这样设计”。

## 10 分钟速记

- 分布式调用不是本地调用：超时、重复、部分失败、版本兼容。
- Kafka 不丢：生产确认 + 副本 + 消费后提交；不重复靠业务幂等。
- 顺序只在分区内；积压先看生产、消费、分区和下游。
- 高可用六件套：超时、限流、隔离、熔断、降级、监控补偿。
