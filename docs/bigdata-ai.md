# Flink、Doris、检索与 AI 工程

> 这页服务于两个项目故事：BFI 的实时数据分析链路，以及 ServiceTag 的大模型 API 集成。Flink、Doris 等不是 JavaGuide 免费主线重点，回答按通用原理和简历场景整理；没有实际负责的部分要明确说“参与”或“方案设计”。

## Flink 高频题

### 1. 为什么 BFI 使用 Flink？

**回答：** BFI 的网络流量和设备数据持续产生，需要低延迟清洗、补字段、关联和状态计算。Flink 提供有状态流处理、事件时间、窗口和 Checkpoint，适合连续数据管道；批量 BCP 文件仍可走独立导入流程，不必把所有任务都强行实时化。

### 2. 事件时间、处理时间和摄入时间有什么区别？

**回答：** 事件时间是数据真实发生的时间，适合业务统计，但会遇到乱序和迟到；处理时间是算子处理数据时机器的时间，实现简单但结果受延迟和重启影响；摄入时间介于两者之间，使用较少。行为分析通常优先事件时间。

### 3. Watermark 是什么？

**回答：** Watermark 是对事件时间进度的估计，表示系统认为早于某时间的数据大部分已经到达，用来触发窗口计算。允许乱序时间越长，结果越完整但延迟越高；迟到数据可配置允许迟到、侧输出或补偿任务，不能简单丢弃。

### 4. 滚动、滑动和会话窗口有什么区别？

**回答：** 滚动窗口长度固定且互不重叠，适合每 5 分钟统计；滑动窗口固定但可以重叠，适合最近 1 小时每 5 分钟更新；会话窗口按事件间隔划分，适合用户一段连续活动。窗口选择必须与业务口径和状态大小匹配。

### 5. Keyed State 和 Operator State 有什么区别？

**回答：** Keyed State 绑定 key，只能在 keyBy 后使用，Flink 能按 key 分区和恢复，适合用户级计数和状态机；Operator State 绑定算子并行实例，适合 source offset 或分片等算子自身状态。状态要设置 TTL，并控制 key 基数和序列化成本。

### 6. Checkpoint 和 Savepoint 有什么区别？

**回答：** Checkpoint 主要由系统周期触发，用于故障自动恢复，生命周期由作业管理；Savepoint 通常由人工触发，用于版本升级、迁移和计划内停止，长期保存。两者都保存一致状态，但目标和运维方式不同。

### 7. Flink Exactly-once 是什么意思？

**回答：** 它表示发生故障和恢复后，每条事件对状态的影响恰好一次，但端到端还要求 Source 可重放、Checkpoint 一致，Sink 支持事务提交或幂等写入。只开启 Checkpoint 不代表 Kafka 到 Doris 整条链路自动 Exactly-once。

### 8. 什么是反压？怎么排查？

**回答：** 下游处理速度跟不上，上游输出缓冲逐步被占满并被迫减速，就是反压。先在 Web UI 找到反压起点，再检查慢算子、外部 I/O、数据倾斜、GC、状态大小和并行度。扩容前要确认下游 Doris 或 Elasticsearch 是否承受得住更高写入速率。

### 9. Flink 数据倾斜怎么处理？

**回答：** 先通过 key 分布和各 subtask 吞吐确认倾斜。热点 key 可拆分成随机前缀做两阶段聚合，维表 Join 可考虑广播，小表缓存要控制更新和内存；业务上也可以单独处理超级热点。盲目增加并行度无法拆开同一个 key。

### 10. Flink 作业失败后如何恢复和补数？

**回答：** 自动恢复从最近成功 Checkpoint 读取状态和 Source offset，Sink 依赖事务或幂等保证不重复生效。超过自动重启策略后告警并保留现场；数据缺口通过可重放 Kafka、原始文件或离线补偿任务处理，并对输入和输出做对账。

## Doris / Elasticsearch / MinIO

### 11. BFI 的数据为什么需要分层？

**回答：** 原始层保留可追溯数据，明细层完成清洗和统一字段，汇总或应用层按画像、碰撞和统计场景预计算。分层能统一口径、减少重复计算并支持问题回溯，代价是链路和存储增加，需要版本及血缘管理。

### 12. 大宽表和预计算有什么取舍？

**回答：** 大宽表减少 Join，预计算减少实时聚合，能显著提升固定场景查询；但会增加数据冗余、更新延迟、口径维护和导入成本。对高频稳定指标使用，对探索性查询保留明细和灵活 Join，不能把所有字段无限摊平。

### 13. Doris 导入如何保证不重复？

**回答：** 根据模型和导入方式使用业务唯一键、版本列、导入 Label 或幂等批次号，失败重试时复用同一标识。还要区分客户端超时但服务端已成功的结果未知场景，先查询导入状态再决定是否重试。

### 14. Elasticsearch 适合什么，不适合什么？

**回答：** 它适合全文检索、复杂过滤、日志检索和近实时聚合，不适合强事务、多表 Join 和作为唯一事实库。BFI 可以用 Elasticsearch 查文本和多条件检索，用 Doris 做大范围分析，权威业务状态仍在事务库或治理后的数仓。

### 15. Elasticsearch 写入后为什么不是立刻可搜？

**回答：** 文档写入后要经过 refresh 才进入可搜索的 segment，因此默认是近实时，不等于强实时。调小 refresh 间隔会增加 segment 和合并开销；批量导入时可以适当调大，完成后恢复。事务可见性要求高的流程不能只依赖 ES。

### 16. MinIO 在项目中适合存什么？

**回答：** MinIO 是对象存储，适合 BCP 文件、导出结果、模型附件和大结果集，不适合频繁随机更新的小记录。上传可使用分片和校验，访问通过短期预签名 URL；元数据、权限和业务状态仍保存在数据库，桶策略遵循最小权限。

## 大模型 API 工程

### 17. ServiceTag 的大模型打标流程怎么讲？

**回答：**

> 我们把服务名称、描述、所属端、已有分类和候选标签组成结构化输入，模型按固定 Schema 返回标签、理由和可选置信信息。服务端解析后执行候选范围、数量和业务规则校验；低置信度或冲突结果进入人工审核，最终结果和修改记录持久化。接口层设置超时、限流、重试和降级，模型异常不会阻塞基础标签管理。

### 18. Prompt 应该包含哪些部分？

**回答：** 包含角色和任务、业务定义、输入字段、可用候选、明确约束、输出 Schema、少量正反例以及无法判断时的行为。Prompt 要版本化并通过固定评测集验证，不能只凭几次手工测试判断效果。

### 19. 如何保证模型结构化输出？

**回答：** 优先使用模型支持的 JSON Schema 或 Tool/Function Calling，把枚举、必填字段和类型写清楚；服务端仍要做解析和业务校验。解析失败可进行一次针对格式的修复或重试，持续失败则降级或人工处理，不能把未经验证的文本直接入库。

### 20. 模型 API 超时或限流怎么处理？

**回答：** 设置连接、读取和整体 Deadline；只对超时、限流等瞬时错误做有限指数退避加抖动，遵守服务端 Retry-After。使用隔离并发、令牌桶和队列控制请求；非实时任务异步执行，失败进入重试队列或人工待办。

### 21. 如何控制模型成本？

**回答：** 先减少无效调用：规则能确定的标签不调用模型，相同输入按模型和 Prompt 版本缓存；压缩上下文，只传必要字段；简单任务使用较小模型，复杂任务升级。监控每类任务的 Token、成功率、重试和人工修正率，不能只看单次价格。

### 22. 如何评估标签准确率？

**回答：** 构建由业务人员确认的评测集，按标签类别和难度分层；统计精确率、召回率、F1、完全匹配率和人工修改率。多标签任务要明确部分命中如何计分；每次 Prompt 或模型升级在同一保留集比较，并对新增线上错误做回归。

### 23. 人工审核如何反哺系统？

**回答：** 保存模型建议、Prompt/模型版本、人工修改、原因和最终标签。高频错误先用于修正规则、候选集和 Prompt，再把高质量审核样例加入检索或评测集。人工修改不能未经清洗直接自动训练，否则会把不一致标准放大。

### 24. RAG 如何帮助标签推荐？

**回答：** 把标签定义、分类规则和已审核相似案例做成知识库，生成前按当前服务检索少量相关内容，模型只在允许的候选中选择。RAG 能补充业务知识，但仍需检索评估、权限隔离和输出校验；如果标签体系很小，规则加候选列表可能比 RAG 更简单可靠。

## 两个项目的 1 分钟版本

### BFI 用户行为分析平台

> 项目处理网络流量、设备上报和批量文件。Kafka 承接实时数据，Flink 完成清洗、字段补充和状态计算，Doris 保存明细及聚合结果，Elasticsearch 支持检索，Redis 缓存热点配置和结果。我的重点是后端核心模块、数据处理链路和查询性能，通过分层、分区分桶、预计算和查询优化支撑大数据量分析。稳定性上关注幂等、Checkpoint、反压、导入状态和补偿。

### ServiceTag 智能服务标签平台

> 项目统一管理 App、小程序和 Web 服务标签。我负责核心后端和大模型 API 集成，将服务信息和候选标签组成结构化 Prompt，模型返回固定格式，服务端校验后进入人工审核。工程上通过超时、限流、有限重试、缓存和降级控制稳定性，审核结果用于评测和后续规则优化。

## 10 分钟速记

- Flink：事件时间 + Watermark，State + Checkpoint，端到端一致要看 Source 和 Sink。
- 反压先找最慢下游，数据倾斜先看 key 分布。
- Doris 做分析，Elasticsearch 做检索，MinIO 放对象。
- AI 工程不是“调 API”：结构化输入输出、校验、评测、观测、人工兜底。
