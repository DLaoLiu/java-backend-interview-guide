# Text2SQL Agent 面试题与参考答案

这套题围绕 **Chat-BFI（Text2SQL Agent）** 展开。回答时不要只背定义，建议使用“原理 → 项目实现 → 风险与取舍”的结构，并明确哪些能力已经实现、哪些属于可演进方案。

::: warning 项目事实优先
本页大部分内容是 Text2SQL 的完整原理和目标方案，不代表 Chat-BFI 已全部实现。项目真实流程、团队、上线状态和技术边界以 [Chat-BFI 项目问答](/projects/chat-bfi-interview) 为准。
:::

## 一、Text2SQL

**1. 请介绍一个完整的 Text2SQL 执行流程。**

参考回答：我会把流程拆成问题理解、Schema Linking、SQL 生成、SQL 校验、受控执行和结果解释六步。问题理解负责提取指标、维度、时间范围和筛选条件；Schema Linking 召回相关表、字段及关联关系；模型基于这些信息生成 SQL；之后通过解析器和 AST 做语法及安全校验，再用只读账号执行；最后对结果进行统计、业务规则计算和自然语言解释。执行失败时，可以把经过脱敏的数据库错误反馈给模型做有限次数的自修复。

**2. 为什么不能直接把用户问题和完整数据库 DDL 一起交给大模型？**

参考回答：完整 DDL 会快速占满上下文，增加 Token、延迟和成本，而且无关表越多，模型选错表和错误 Join 的概率越高。生产系统应该先检索与问题相关的 Schema，只提供必要的表、字段、注释、枚举值和关联关系，同时用权限过滤避免未授权 Schema 进入模型上下文。

**3. 问题理解阶段需要识别哪些信息？**

参考回答：至少要识别业务主题、指标、维度、时间范围、筛选条件、排序、粒度、返回数量以及查询意图。例如“近半年各部门风险人数趋势”需要识别时间是近六个月、粒度是月、维度是部门、指标是风险人数、意图是趋势分析。信息缺失且会影响口径时，应先澄清而不是猜测。

**4. 如何判断一个问题是趋势查询还是明细查询？**

参考回答：趋势查询通常包含“变化、走势、同比、环比、按月”等表达，输出是按时间或维度聚合的指标；明细查询通常包含“哪些人、列出记录、详情”等表达，输出是实体列表。项目中可以先用规则识别强特征，再由模型输出结构化意图；路由结果置信度低或同时包含两类意图时，可以拆成两个子任务。

**5. 趋势查询和明细查询在 SQL 生成上有什么区别？**

参考回答：趋势 SQL 重点是时间分桶、聚合函数、`GROUP BY`、排序以及同比环比所需的窗口计算；明细 SQL 重点是字段投影、精确过滤、稳定排序、分页和敏感字段控制。趋势查询一般返回较少的聚合行，明细查询必须强制限制行数，避免拉取大量记录。

**6. Text2SQL 中最容易出现哪些错误？**

参考回答：常见错误分为四类：语法错误，例如函数或方言不兼容；Schema 错误，例如表字段不存在；语义错误，例如时间口径、聚合粒度或 Join 条件错误；安全和性能错误，例如访问敏感表、全表扫描或返回过多数据。语法校验只能覆盖第一类，结果正确性还需要业务规则、样例集和执行结果检查。

**7. SQL 语法正确是否意味着查询结果正确？为什么？**

参考回答：不意味着。SQL 可以成功执行，但可能选错指标字段、漏掉租户条件、使用错误的时间字段、重复 Join 导致指标放大，或者把“人数”写成记录数。生产评估不能只看执行成功率，还要验证结果和业务口径是否正确。

**8. SQL 生成后需要经过哪些校验？**

参考回答：先解析 SQL，确认是允许的查询语句；再基于 AST 校验表字段白名单、禁止的函数和系统表、子查询深度、Join 数量及租户条件；之后检查是否有行数限制和超时配置，必要时执行 `EXPLAIN` 估算扫描风险。执行账号还要保持只读，形成应用校验和数据库权限两层防线。

**9. 如何处理“最近半年”“上季度”等时间表达？**

参考回答：先以服务端确定的当前日期和业务时区做时间标准化，转换为明确的起止时间，并说明闭开区间。例如“上季度”应按自然季度计算，而不是简单减三个月。相对时间最好由代码工具计算后传给模型，减少模型日期计算错误。

**10. 如何处理“重点人员”“风险客户”这类业务语义？**

参考回答：这类词不是通用数据库概念，必须映射到经过确认的业务口径。可以在语义层维护术语、指标定义、计算规则和对应字段；确定性的风险规则由代码或 SQL 执行，模型负责理解用户表达和解释结果，不能让模型临时发明风险标准。

**11. SQL 执行结果为空时，Agent 应该如何处理？**

参考回答：不能直接断言“没有数据”。应区分确实无数据、筛选条件过严、Schema 或字段映射错误、权限过滤以及数据延迟。Agent 可以检查时间范围和关键过滤条件，必要时执行低成本的诊断查询；仍无法判断时，向用户说明当前条件下未查询到数据并建议调整条件。

**12. 如何让模型解释查询结果，而不是简单复述数据？**

参考回答：先由代码计算总量、占比、极值、变化率和异常点，再把结构化统计摘要交给模型，并要求结论绑定具体证据。模型只解释已计算的事实，不自行补数；大结果集先聚合和截断，并在回答中注明数据范围及口径。

**13. 如果同一个问题可以生成多条 SQL，如何选择最可靠的一条？**

参考回答：可以生成少量候选 SQL，先做 AST、安全和执行检查，再根据 Schema 匹配度、业务口径覆盖度、执行代价及小样本结果进行排序。更成熟的方式是用验证器对问题、SQL 和结果做一致性判断，但最终仍要用离线金标集证明这种选择策略有效。

**14. SQL 查询需要多表关联时，如何降低 Join 错误率？**

参考回答：把经过治理的主外键、实体关系、Join 方向和基数作为 Schema 元数据，而不是只给模型字段名。对高频查询可以提供受控视图或语义模型，减少临时 Join；执行前还可以检查缺失 Join 条件、潜在笛卡尔积和一对多关系造成的重复聚合。

**15. Text2SQL 是否适合直接用于写操作？为什么？**

参考回答：默认不适合。模型的不确定性可能造成不可逆的数据修改，即使 SQL 语法正确也可能影响错误范围。如果业务必须支持写操作，应与只读查询链路隔离，使用最小权限、事务、影响行数预估、显式人工审批、审计和回滚机制。

## 二、Schema Linking

**1. 什么是 Schema Linking？它解决什么问题？**

参考回答：Schema Linking 是把自然语言中的业务实体、指标和条件映射到数据库表、字段、枚举值以及表间关系的过程。它解决用户说的是业务语言、数据库保存的是技术结构之间的鸿沟，是降低选错表、字段和 Join 的关键环节。

**2. 如何将用户问题映射到对应的表和字段？**

参考回答：先对问题提取关键词和业务实体，再从表名、字段名、中文注释、指标定义、枚举值及历史样例中做混合检索，得到候选 Schema。之后结合租户权限、表关系和问题意图重排，只把高相关候选交给 SQL 生成节点。

**3. Schema 检索一般需要保存哪些元数据？**

参考回答：包括库表名、字段名、数据类型、注释、主外键、表关系、枚举值、时间字段、指标口径、数据粒度、敏感等级、权限标签和常用查询样例。还应记录 Schema 版本和更新时间，便于数据结构变更后重建索引。

**4. 关键词检索和向量检索分别适合什么场景？**

参考回答：关键词检索适合精确表名、字段名、编码和固定术语，结果可解释；向量检索适合同义词和自然语言描述，例如“员工”匹配“人员信息”。生产中通常采用混合召回，再结合业务域、权限和关系做重排，不能只依赖向量相似度。

**5. 如何将字段注释、业务名称和枚举值用于 Schema 检索？**

参考回答：可以把字段的技术名、中文名、定义、所属表和代表性枚举组织成一条可检索文档。例如 `risk_level` 同时关联“风险等级、高风险、中风险、低风险”。枚举只能选择低敏感且有助于匹配的值，不应把真实个人数据写进向量库。

**6. 多张表中存在同名字段时，如何选择正确字段？**

参考回答：不能只看字段名，要结合表的业务域、数据粒度、字段描述、与其他候选字段的关系以及问题中的实体判断。对于 `status` 这类通用字段，应把完整限定名和枚举含义提供给模型，必要时通过业务语义层明确优先映射。

**7. 如何确定表之间的关联关系？**

参考回答：优先使用数据库外键和数据治理平台维护的关系；没有显式外键时，可以结合字段命名、数据字典、ETL 逻辑和人工确认补充关系元数据。关系中要记录 Join 键、方向、基数和适用条件，避免模型仅凭同名字段猜测。

**8. 外键不完整或者数据库没有显式外键时怎么办？**

参考回答：建立独立的 Schema 关系注册表，由数据开发或业务负责人维护可信 Join 路径。可以从历史 SQL 中挖掘候选关系，但候选必须经过验证后才能进入生产语义层，不能直接把自动推断结果当成事实。

**9. Schema 检索召回的表太多会产生什么问题？**

参考回答：会增加 Token、延迟和模型干扰，导致选错表、虚构关系或生成复杂 SQL。通常先按业务域粗筛，再做字段级召回和关系扩展，并设置表数、字段数上限；相关性不足时应澄清，而不是无限扩大候选。

**10. 如何评价 Schema Linking 的效果？**

参考回答：离线可以统计正确表和字段的 Recall@K、Precision@K，以及正确 Join 路径的召回率；在线要结合 SQL 执行正确率、结果正确率、澄清率和人工介入率。只看向量相似度没有意义，最终要看正确 Schema 是否进入了生成上下文。

**11. 如何处理业务术语与数据库字段名称不一致的问题？**

参考回答：维护业务术语表或轻量语义层，把术语、同义词、指标定义和物理字段建立映射，并把人工修正沉淀为样例。例如“重点人员”应映射为明确的规则或视图，而不是让模型从字段名猜。

**12. 是否会把样例数据加入 Schema 上下文？有什么风险？**

参考回答：少量枚举和脱敏样例有助于理解字段语义，但真实样例可能包含个人信息、扩大上下文并诱导模型过拟合。应该只提供经过权限过滤、脱敏和截断的数据，敏感字段尽量只提供类型与定义。

**13. 数据库 Schema 发生变化后，如何更新检索索引？**

参考回答：通过定时任务或元数据变更事件检测 DDL，生成带版本的 Schema 快照并增量重建索引。新索引验证通过后原子切换，旧版本保留短期回滚；同时让执行错误监控能够识别字段变更导致的集中失败。

**14. 如何防止模型查询未授权的表或字段？**

参考回答：检索前按用户和租户权限过滤 Schema，生成后再用 AST 对表字段做白名单校验，执行账号本身也使用最小权限。查询结果进入模型前还要做字段级脱敏，不能把权限控制只放在 Prompt 中。

## 三、LangGraph

**1. 为什么项目使用 LangGraph，而不是直接串联 LangChain Chain？**

参考回答：Chat-BFI 不是固定的线性链路，它包含相关性判断、趋势与明细分支、失败重试、人工中断和恢复。LangGraph 用显式状态和图描述这些分支、循环及终止条件，更便于观测、测试和持久化；LangChain 仍可以用于节点内部的模型和 Tool 封装。

**2. LangGraph 中 State、Node 和 Edge 分别是什么？**

参考回答：State 是节点之间共享且可持久化的数据，例如问题、意图、Schema、SQL、结果和重试次数；Node 是执行一个明确职责的函数；Edge 决定节点执行顺序，条件 Edge 根据 State 路由。设计重点是让节点职责单一、状态字段有明确所有者。

**3. Chat-BFI 的 State 中保存了哪些字段？**

参考回答：可以包含 `session_id`、当前问题、标准化意图、相关性、查询类型、时间范围、候选 Schema、生成 SQL、校验结果、查询结果引用、统计摘要、重试次数、人工审批状态和错误信息。大结果集不直接塞入 State，而保存对象存储或缓存引用。

**4. 如何设计问题相关性判断节点？**

参考回答：输入是当前问题、少量会话摘要和 BFI 业务范围，输出使用结构化字段，例如 `relevant`、`reason` 和 `confidence`。强规则先拦截明显无关内容，模型处理语义边界；低置信度进入澄清或友好提示，并用误判样例持续评测。

**5. 如何实现趋势查询和明细查询的条件分支？**

参考回答：意图节点输出受枚举约束的 `query_type`，条件 Edge 根据该字段进入趋势 SQL 或明细 SQL 节点。路由判断与具体 SQL 生成分离，便于单独评测；混合意图则拆为子任务或进入组合分支。

**6. 条件 Edge 的判断结果由模型产生还是由代码产生？**

参考回答：语义判断可以由模型产生，但结果必须是结构化枚举；Edge 本身由确定性代码读取该枚举并路由。安全、重试次数和审批状态等控制条件应由代码判断，不能让模型决定是否绕过安全流程。

**7. 如何在 LangGraph 中实现 ReAct 循环？**

参考回答：模型节点根据当前 State 选择 Tool，Tool 节点执行并把 Observation 写回 State，再由条件 Edge 判断是继续推理、重新生成还是结束。State 中要保存迭代次数、已调用工具和最近错误，避免无效重复。

**8. 如何避免 Agent 在图中无限循环？**

参考回答：设置图级递归上限和业务级最大迭代次数，并识别相同 SQL、相同错误或相同 Tool 参数的重复调用。达到阈值后进入失败处理或人工节点，返回可解释的终止原因。

**9. 什么是 Checkpoint？它解决什么问题？**

参考回答：Checkpoint 是某一步执行后的图状态快照，使流程能够按线程或会话恢复。它用于故障恢复、人工中断后继续以及长流程状态保存，但不等同于完整聊天记录，也不能替代业务数据库。

**10. Checkpoint 与业务数据库中的会话记录有什么区别？**

参考回答：Checkpoint 服务于工作流执行，保存节点恢复所需的状态；会话记录服务于产品功能和审计，保存用户消息、回答及业务元数据。二者生命周期、查询方式和合规要求不同，可以通过 `session_id` 或 `thread_id` 关联。

**11. LangGraph 节点执行失败后如何恢复？**

参考回答：先区分可重试的临时错误和不可重试的业务错误。可重试错误使用有限次数和退避策略，从最近的 Checkpoint 继续；不可重试错误进入兜底或人工节点。节点涉及外部写入时必须带幂等键，防止恢复后重复执行。

**12. 哪些节点应该保证幂等性？**

参考回答：所有可能重试且有外部副作用的节点都应幂等，例如写会话记录、提交审批、调用计费服务和发送通知。只读查询虽然不修改数据，也应通过请求标识避免重复消耗资源；纯模型调用可缓存但要考虑随机性和模型版本。

**13. 如何实现中断后等待人工确认，再从原节点继续执行？**

参考回答：在高风险节点前生成审批内容并触发中断，把图状态写入持久化 Checkpointer。人工操作通过同一 `thread_id` 更新审批结果，然后使用恢复命令继续执行；恢复节点必须再次校验审批内容与待执行 SQL 是否一致。

**14. 多个节点同时更新 State 时如何避免状态覆盖？**

参考回答：为 State 字段定义合并策略或 reducer，并让每个节点只返回自己负责的增量字段。并行分支写同一字段时要使用列表追加、版本号或显式汇总节点，不能依赖最后写入覆盖。

**15. LangGraph 状态中是否应该保存完整查询结果？为什么？**

参考回答：小结果可以保存，但大结果不应该。完整结果会让 Checkpoint 体积、序列化成本和敏感数据风险快速增长；更合理的方式是保存结果集 ID、缓存地址、行列摘要和统计结果，并设置访问权限与过期时间。

**16. 如何对某一个节点单独进行测试？**

参考回答：为节点构造最小 State，Mock 模型、数据库和 Tool，断言节点的增量输出以及异常分支。路由节点要覆盖每个枚举和边界值；再使用固定数据集做图级集成测试，避免只测试 Prompt。

**17. 如何设计 Agent 的终止条件？**

参考回答：正常终止包括成功返回、确认问题无关或用户主动取消；异常终止包括超过迭代次数、连续相同错误、安全校验失败和人工拒绝。终止状态应包含机器可读状态码和用户可理解的说明，便于监控与恢复。

## 四、ReAct 与错误自修复

**1. 请解释 ReAct 中 Reasoning、Action、Observation 的关系。**

参考回答：模型先根据目标和当前状态判断下一步，选择一个 Action，例如查询数据库或执行统计工具；工具返回 Observation 后，模型再决定继续调用工具还是生成答案。工程上更关注可观测的动作、参数和结果，不应把模型的隐藏推理过程直接展示或持久化。

**2. Chat-BFI 中有哪些能力适合封装成 Tool？**

参考回答：Schema 检索、时间范围标准化、SQL 校验、只读查询、结果统计、业务规则计算和审批提交都适合封装为边界清晰的 Tool。每个 Tool 要有严格的输入输出 Schema、权限控制、超时和错误码，避免做成可以任意执行代码或 SQL 的万能工具。

**3. 模型如何决定调用 SQL 查询工具还是统计分析工具？**

参考回答：工具描述应明确前置条件：没有数据时先调用查询工具，State 中已有结果摘要后才能调用统计工具。代码还会校验调用顺序，例如统计 Tool 必须携带有效的结果集 ID，不能只依赖模型自觉遵循 Prompt。

**4. Tool 返回值应该直接返回数据库原始结果吗？**

参考回答：不应该无条件返回。Tool 应返回结构化、截断且脱敏的结果，包含列定义、行数、少量样例、统计摘要和结果集引用。这样可以控制上下文、降低隐私风险，并让后续节点明确数据是否被截断。

**5. SQL 执行失败后，如何利用错误信息进行自修复？**

参考回答：先把数据库错误标准化，保留错误类型、位置和相关 Schema，删除连接信息等敏感内容；再连同原 SQL 和问题反馈给生成节点。新 SQL 必须重新经过全部安全校验，且 State 中增加重试次数并记录失败历史。

**6. 哪些数据库错误可以自动重试，哪些不应该重试？**

参考回答：字段名错误、函数方言不兼容等可尝试重新生成；瞬时连接失败和超时可按策略重试执行，但 SQL 本身过重时应先优化。权限拒绝、安全策略命中、人工拒绝和确定性的业务校验失败不应通过模型反复绕过。

**7. 为什么需要限制 Agent 的最大重试次数？**

参考回答：模型可能陷入相同错误循环，每次重试都会增加延迟、Token 和数据库压力。最大次数应按错误类型配置，并配合重复 SQL 指纹检测；达到阈值后返回明确原因或转人工。

**8. 重试时应该把哪些信息反馈给模型？**

参考回答：反馈原始问题、当前使用的 Schema、失败 SQL、标准化错误、数据库方言、之前尝试的差异以及不可违反的约束。不要把数据库凭据、内部地址、完整堆栈和未授权 Schema 放入 Prompt。

**9. 如何避免模型每次重试都生成相同 SQL？**

参考回答：保存 SQL 规范化后的指纹和错误历史，在 Prompt 中明确指出上次失败原因，并要求输出修复说明及新 SQL。若指纹连续相同，直接终止该自动修复路径，而不是继续消耗模型调用。

**10. SQL 执行成功但结果明显异常时，如何触发重新生成？**

参考回答：设置结果级守卫，例如结果为空、数量超过业务上限、关键字段全为空、聚合值异常放大或趋势时间点缺失。守卫命中后先做诊断查询并检查口径；只有证据指向 SQL 问题时才重新生成，不能因为结果“不符合预期”就篡改事实。

**11. 如何防止 ReAct 过程泄露内部推理或敏感数据？**

参考回答：对外只返回结论、证据和简短执行说明，不暴露隐藏思维链。Trace 中记录节点、工具、Token 和必要的输入输出摘要，敏感字段脱敏并设置访问权限和保留周期。

**12. 如果模型连续调用无效工具，系统应该如何终止？**

参考回答：通过调用次数、重复参数和前置条件错误计数识别无效循环。达到阈值后进入终止节点，返回当前已完成内容、失败原因和可执行建议，同时把该案例标记为评测或 Prompt 优化样本。

## 五、Human-in-the-Loop

**1. Chat-BFI 中哪些节点需要人工确认？**

参考回答：只读且低风险的常规查询可以自动执行；访问高敏感字段、超大范围查询、低置信度 Schema 映射、可能影响重点人员判定的结果，以及任何写操作都应进入审批。是否审批由代码策略基于风险等级决定，不由模型自行决定。

**2. 为什么写操作必须比查询操作采用更严格的审批机制？**

参考回答：写操作有不可逆或大范围副作用，模型误解一个条件就可能污染业务数据。除人工审批外，还需要最小权限、事务、影响行数预览、幂等键、审计和回滚；最好与 Text2SQL 只读账号和执行通道完全隔离。

**3. 如何判断一条 SQL 属于高风险 SQL？**

参考回答：基于 AST 识别语句类型、目标表、敏感字段、是否缺少租户和时间条件、影响范围、Join 复杂度以及预计扫描量。风险评分应由明确规则计算，模型可以解释风险，但不能覆盖硬性策略。

**4. 模型置信度达到多少可以自动执行？阈值如何确定？**

参考回答：没有通用的固定阈值。要在带真实分布的验证集上校准置信度，比较不同阈值下的错误成本、自动化覆盖率和人工介入率；高风险场景阈值更高，且模型自报置信度不能单独作为依据。

**5. 人工确认期间，Agent 状态保存在哪里？**

参考回答：图恢复所需状态保存在持久化 Checkpointer，审批单和操作审计保存在业务数据库。二者通过审批 ID 和 `thread_id` 关联，并设置状态版本，防止审批期间原 SQL 被替换。

**6. 用户修改模型生成的 SQL 后，流程如何继续？**

参考回答：修改后的 SQL 被视为新的候选版本，重新执行 AST、安全、权限和性能校验，不能直接运行。审批记录要保存原 SQL、修改后 SQL、修改人和时间，执行时校验审批的 SQL 哈希。

**7. 人工拒绝执行后，是否应该重新生成 SQL？**

参考回答：取决于拒绝原因。若原因是条件或字段错误，可以把结构化反馈用于一次新生成；若因权限或业务策略拒绝，则终止流程，不能让模型尝试规避限制。

**8. 如何记录人工介入原因，并用于后续优化？**

参考回答：介入事件保存节点、风险类型、模型输出、修改内容、最终结果和原因标签。定期按标签分析，例如 Schema 误召回、时间口径不清或安全误报，再用于扩充评测集、修正元数据和调整策略，而不是未经审核就自动训练。

**9. Human-in-the-Loop 会影响响应时间，如何权衡安全与体验？**

参考回答：采用风险分级：低风险自动执行，中风险展示 SQL 或口径供快速确认，高风险走正式审批。审批界面应突出影响范围和风险原因，并支持异步通知及恢复，避免请求一直占用 HTTP 连接。

## 六、会话记忆

**1. 当前上下文缓存、历史会话持久化和业务状态有什么区别？**

参考回答：当前上下文缓存服务于短期推理，保存最近消息和摘要；历史持久化服务于查询、审计和跨会话恢复；业务状态是任务的结构化事实，例如当前时间范围、结果集 ID 和审批状态。三者需要不同的存储、过期和权限策略。

**2. Chat-BFI 如何实现多轮对话中的指代消解？**

参考回答：在 State 中保存上一轮标准化意图、指标、筛选条件和结果集引用，新问题先判断是延续、修改还是新主题。例如“只看其中风险最高的十个人”会继承上一轮人群和时间条件，只新增排序与限制。

**3. 用户说“只看其中风险最高的十个人”时，如何关联上一轮结果？**

参考回答：先确认“其中”指向上一轮哪个结果集，读取其查询条件或结果集 ID，再追加风险排序和 `LIMIT 10`。不能只把上一轮自然语言回答拼回 Prompt，因为回答可能丢失原始口径。

**4. 为什么不能把所有历史消息一直放进 Prompt？**

参考回答：上下文会持续增长，带来成本、延迟和超限问题，早期错误还会污染后续推理。通常保留最近若干轮、结构化业务状态和滚动摘要，重要事实单独持久化。

**5. 如何控制上下文长度和 Token 成本？**

参考回答：设定消息窗口和 Token 预算，旧消息做摘要；Schema 按问题检索；查询结果只保留统计摘要和引用；固定系统说明复用或缓存。还要监控每个节点的 Token，而不是只看整次请求。

**6. 历史对话可以采用哪些压缩方式？**

参考回答：可以使用最近消息窗口、滚动摘要、按主题分段、实体和槽位抽取，以及仅检索相关历史。摘要应保留指标、时间、筛选条件、用户确认和未完成任务，并注明来源轮次，避免摘要变成新的错误事实。

**7. 哪些信息应该持久化，哪些信息只需要临时缓存？**

参考回答：用户消息、最终回答、SQL、口径、审批和审计信息通常需要持久化；模型中间草稿、大型原始结果和可重新计算的临时数据只短期缓存。是否持久化还要遵循数据分级、用户删除和保留周期要求。

**8. Redis、关系型数据库和 LangGraph Checkpoint 分别适合保存什么？**

参考回答：Redis 适合短期上下文、锁和结果缓存；关系型数据库适合会话记录、审批、审计和可查询的业务状态；Checkpoint 适合图执行恢复。Checkpoint 的后端可以使用数据库，但逻辑职责仍要区分。

**9. 多轮会话中如何防止上一轮 Schema 或 SQL 污染当前问题？**

参考回答：先做话题延续判断，只有被确认继承的槽位才进入当前标准化意图。每一轮都重新执行权限过滤和 Schema Linking；上一轮 SQL 只能作为参考，不能跳过当前轮校验。

**10. 用户切换话题后，如何重置或隔离上下文？**

参考回答：检测新问题与当前业务主题、实体和指标的相关度，低于阈值时创建新的任务上下文，清除继承槽位但保留会话历史。用户也可以显式发起“新分析”，生成新的 thread 或 task ID。

**11. 会话状态如何设置过期时间？**

参考回答：按数据用途分层设置：在线上下文较短，结果缓存按数据敏感度和复用需求设置，审计记录按合规要求保留。过期时要同步清理结果引用和敏感临时文件，不能只删除 Redis 中的指针。

**12. 服务重启后如何恢复未完成的 Agent 任务？**

参考回答：使用持久化 Checkpoint 保存最近成功节点和状态，任务表记录运行、等待审批、失败等状态。重启后扫描可恢复任务，基于幂等键继续；正在执行但无法确认结果的外部调用要先做状态查询，避免重复执行。

## 七、SQL 安全

**1. Text2SQL 系统可能面临哪些安全风险？**

参考回答：包括模型生成写操作、越权访问、SQL 注入、Prompt Injection、敏感数据泄露、超大查询拖垮数据库、跨租户查询和 Trace 泄密。安全必须覆盖 Prompt 前、SQL 执行前、数据库权限、结果返回及可观测平台全链路。

**2. 为什么 Agent 应该使用只读数据库账号？**

参考回答：应用校验可能被绕过或存在缺陷，只读账号提供数据库侧的最终防线。账号还应限制可访问库表、查询资源和并发，最好连接只读副本或分析库，避免影响交易系统。

**3. 如何通过 SQL AST 判断 SQL 是否安全？**

参考回答：使用对应方言的解析器把 SQL 转为 AST，遍历语句类型、表、字段、函数、子查询和条件。只允许白名单中的 `SELECT` 结构，拒绝 DDL、DML、多语句、系统表和危险函数，并检查租户条件及行数限制。

**4. 为什么只用字符串匹配拦截 `DELETE`、`UPDATE` 不可靠？**

参考回答：字符串可以通过大小写、注释、编码、嵌套或方言语法绕过，也可能误伤字段别名。AST 基于语法结构判断更可靠，但仍要配合数据库只读权限，因为解析器也可能有方言覆盖不足。

**5. 如何实现表和字段白名单？**

参考回答：白名单按用户角色、租户和业务域生成，Schema 检索只返回授权对象，AST 再验证 SQL 中实际引用的所有表字段。视图展开、通配符和子查询也要处理，`SELECT *` 在敏感场景应禁止。

**6. 如何限制查询返回行数？**

参考回答：在 AST 层统一注入或收紧 `LIMIT`，并在驱动层设置最大行数和流式读取限制。明细查询使用稳定排序和分页；聚合查询也要限制分组基数，不能认为有 `GROUP BY` 就一定安全。

**7. 如果模型生成的 SQL 已经包含 `LIMIT`，应该如何处理？**

参考回答：解析现有值并取它与系统上限中的较小值，不能简单追加第二个 `LIMIT`。同时处理方言差异、子查询内的 `LIMIT`，确保限制作用在最终结果集。

**8. 如何设置 SQL 执行超时？**

参考回答：数据库会话或语句级设置执行超时，连接池设置获取连接和网络读取超时，应用层再设置整体 Deadline。超时后要取消数据库端查询，不能只让 HTTP 请求返回而 SQL 继续运行。

**9. 如何防止笛卡尔积或全表扫描？**

参考回答：AST 检查 Join 是否存在条件、是否使用可信关系；执行前用 `EXPLAIN` 检查扫描行数、分区裁剪和估算成本。超过阈值时拒绝或要求缩小时间范围，高频分析则使用索引、物化视图或分析型数据库。

**10. 如何识别敏感字段并进行脱敏？**

参考回答：在元数据中维护字段敏感等级和脱敏策略，例如身份证、手机号按角色做掩码或哈希。权限判断在查询前执行，结果进入日志、模型和 Langfuse 前再次脱敏，避免只处理最终页面。

**11. 如何防止用户通过自然语言实施 Prompt Injection？**

参考回答：把用户输入视为不可信数据，系统规则与用户文本隔离；模型只能调用输入 Schema 严格、权限受控的 Tool。用户要求“忽略规则”不会改变白名单、AST 校验和数据库权限，检索到的外部文本也按不可信内容处理。

**12. 如何防止 SQL 查询绕过字段权限？**

参考回答：AST 解析所有投影、过滤、排序、函数参数、子查询和 Join 中引用的字段，不只检查 `SELECT` 列。更稳妥的方式是提供按角色裁剪的安全视图，并让执行账号本身无法读取原始敏感列。

**13. SQL 参数应该如何绑定，避免注入风险？**

参考回答：用户提供的值通过参数化查询绑定，不能直接拼接进 SQL；表名、字段名等标识符不能作为普通参数，应从白名单映射。即使 SQL 由模型生成，运行前也应把可变量值抽取为参数并验证类型。

**14. 查询结果进入模型前还需要进行哪些安全处理？**

参考回答：按权限做列级和行级过滤，敏感值脱敏，限制行列数，清除可能携带指令的自由文本，并标记数据来源和截断状态。发送到第三方模型前还要满足数据出境、保留和供应商合规要求。

## 八、Langfuse 与效果评估

**1. 为什么需要为 Agent 引入 Langfuse？**

参考回答：Agent 一次请求包含多个模型、Tool 和分支调用，只看接口日志很难还原问题。Langfuse 可以把整条链路关联起来，记录 Prompt 版本、模型、Token、延迟、工具参数摘要、错误和评估分数，用于排障、成本分析和版本对比。

**2. Langfuse 中 Trace、Span 和 Generation 分别表示什么？**

参考回答：Trace 表示一次完整用户任务；Span 表示其中一个步骤，例如 Schema 检索或 SQL 执行；Generation 专门表示一次模型调用，记录模型、输入输出、Token、延迟和成本。Chat-BFI 可以用一次 API 请求作为 Trace，各 LangGraph 节点作为 Span。

**3. 如何追踪一次请求经过的全部 LangGraph 节点？**

参考回答：入口生成或透传统一的 Trace ID，并把会话 ID、用户匿名标识和 Prompt 版本作为元数据。每个节点创建子 Span，模型调用作为 Generation，Tool 调用记录耗时和状态；异步或恢复执行时继续关联原 Trace 或通过任务 ID 建立链接。

**4. 需要记录哪些模型调用指标？**

参考回答：记录模型及版本、Prompt 版本、输入输出 Token、首 Token 和总延迟、重试、错误、缓存命中、成本及结构化输出解析结果。业务侧还要记录路由正确性、SQL 是否通过校验和最终任务状态。

**5. 如何关联用户请求、会话、SQL 和模型调用链路？**

参考回答：使用 `request_id` 标识单次请求，`session_id` 标识会话，`thread_id` 标识图执行，`sql_id` 标识 SQL 版本，并全部关联到 Trace。外部日志和数据库审计也记录这些 ID，才能跨系统定位问题。

**6. 是否应该把完整 SQL 和查询结果上传到 Langfuse？**

参考回答：不能默认上传。SQL 可能包含敏感条件，结果更可能含个人数据；通常记录 SQL 模板、哈希、表字段集合、行数和脱敏样例。确需保存完整内容时要有访问控制、加密、保留周期和合规依据。

**7. 如何对敏感数据进行脱敏后再上报？**

参考回答：在埋点 SDK 外封装统一处理层，根据字段元数据做掩码、哈希或删除，并对自由文本做规则和实体识别。脱敏应在数据离开业务服务前完成，不能依赖 Langfuse 页面侧隐藏。

**8. 如何定位 Agent 响应慢的问题？**

参考回答：先按 Trace 拆分各节点耗时，区分模型排队与生成、Schema 检索、数据库执行、重试和人工等待。再结合 Token、SQL 扫描量和调用次数定位根因，例如上下文过大、慢 SQL或无效 ReAct 循环。

**9. Text2SQL 应该关注哪些核心评估指标？**

参考回答：离线关注 Schema Recall、SQL 执行正确率、结果正确率和安全通过率；在线关注任务完成率、澄清率、平均迭代次数、人工介入率、P95 延迟、成本和用户反馈。核心指标应优先是结果与任务，而不是 SQL 字符串完全一致。

**10. SQL 执行正确率和结果正确率有什么区别？**

参考回答：执行正确率表示 SQL 能否成功运行，字段和语法错误会降低它；结果正确率表示返回的数据是否符合问题和业务口径。错误 Join 或时间范围也许能成功执行，但结果是错的，所以后者更接近真实价值。

**11. 如何构建 Text2SQL 离线评测集？**

参考回答：从脱敏后的真实问题中按业务域、难度和查询类型分层采样，由业务和数据人员确认问题、口径、授权 Schema、参考 SQL 或期望结果。评测集要包含歧义、空结果、安全攻击、方言和多轮问题，并划分开发集与长期保留测试集。

**12. 如何评价存在多种正确写法的 SQL？**

参考回答：不要只做字符串完全匹配。可以在固定快照数据上比较执行结果，并补充规范化 AST、关键表字段、过滤条件和聚合粒度检查；对于顺序无关结果，需要先按业务键排序或集合化比较。

**13. 任务完成率应该如何定义？**

参考回答：定义为用户目标在允许的交互次数内被正确完成的比例，包括必要澄清和合规拒绝，而不是只统计接口返回 200。成功条件应按任务类型明确，例如趋势题需要正确口径、数据和解释。

**14. 平均迭代次数过高通常说明什么？**

参考回答：可能是 Schema 召回不准、Prompt 约束不足、工具描述不清、模型能力不匹配或数据库错误没有标准化。要按失败类型分组查看迭代分布，不能简单提高最大次数。

**15. 人工介入率过高应该如何优化？**

参考回答：先区分合理的高风险审批和可避免的低置信度介入。对后者分析常见原因，优先改进 Schema 元数据、业务术语、澄清策略和评测；降低介入率不能以放松安全阈值为代价。

**16. 如何通过 Langfuse 对比不同 Prompt 或模型版本？**

参考回答：给每次 Generation 标记 Prompt、模型和配置版本，在同一冻结评测集上运行实验，对比结果正确率、安全失败率、延迟、Token 和成本。上线时做小流量灰度并监控分业务域表现，不能只比较平均分。

**17. 如何避免 Prompt 优化造成评测集过拟合？**

参考回答：开发集用于调试，保留集只在里程碑评估；定期从新线上问题构建时间外测试集，并按业务域观察泛化。Prompt 中不能直接包含测试题答案，人工分析也要记录版本和变更原因。

## 九、Chat-BFI 项目高频题

**1. 请用两分钟介绍 Chat-BFI 项目的背景、功能和你的职责。**

参考回答：

> Chat-BFI 是公司内部开发的 BFI 对话式分析 Agent，团队由一名前端和一名后端组成，我负责后端。流程先判断问题是否属于 BFI 业务，再规范输入、召回并重排相关 Schema，由模型生成结构化任务计划。计划经过人工确认后逐步生成和执行 SQL，最后结合各步骤结果总结。项目后来因部门调整和业务线取消而没有上线。
>
> 我主要负责 FastAPI 服务、LangChain 模型与 Tool 封装、LangGraph 有状态流程、PostgreSQL Checkpoint 和 Langfuse 链路观测。当前 SQL 只完成语法及趋势/明细特征校验；AST、最小权限、超时和执行计划检查属于后续演进。

如果某项能力没有实际上线，要把“已实现”和“设计方案”分开表达。

**2. 请画出从用户问题到最终分析结果的完整架构。**

参考回答：入口是 FastAPI，LangGraph 依次执行相关性判断、输入规范化、Schema 召回与重排、结构化任务规划和人工确认。确认后按计划逐步执行 SQL 生成、语法及查询类型特征校验、Doris 查询；失败最多重试三次。每步通过带过期登记的逻辑 View 暴露给后续步骤，最后由模型总结。Checkpoint 保存在 PostgreSQL，Langfuse 记录链路。

**3. 为什么这个项目需要 Agent，而不是普通的问答系统？**

参考回答：普通问答主要生成文本，而这个任务需要根据状态选择工具、访问实时业务数据、校验 SQL、处理执行错误、调用统计规则并在高风险时暂停审批。Agent 的价值是编排这些受控动作，不是让模型拥有无限自主权。

**4. Chat-BFI 的 LangGraph 包含哪些节点？**

参考回答：实际节点包括相关性判断、输入规范化、Schema 召回与重排、任务规划、人工确认、SQL 生成、语法校验、趋势/明细特征校验、SQL 执行和总结。SQL 失败回到生成节点，最多三次；用户否决计划时补充信息并回到规划节点。

**5. 问题相关性判断是如何实现的？**

参考回答：当前由模型判断问题是否属于 BFI 业务，不相关问题返回友好提示。规则预判、置信度灰区和独立评测集属于可继续完善的能力，不能说成已经实现。

**6. 如何降低相关性判断的误判率？**

参考回答：明确业务边界并补充正负样例，对含指代的多轮问题带上必要会话状态，按错误案例更新术语表。策略上设置灰区而不是强制二分类，对灰区先澄清；同时分别监控误拒率和误放率。

**7. 趋势查询和明细查询的路由规则是什么？**

参考回答：先由模型判断趋势或明细，再由固定校验逻辑检查 SQL 特征。趋势查询应具有时间粒度和聚合函数；明细查询应返回具体记录。分类与 SQL 特征不一致时重新生成，混合需求回到计划阶段拆成依赖步骤。

**8. 为什么将趋势查询和明细查询设计成两个分支？**

参考回答：两类查询的 SQL 模板、行数控制和后处理明显不同。趋势分支强调时间分桶、聚合与变化率，明细分支强调字段权限、分页和敏感信息；分开后 Prompt 更聚焦，评测和安全策略也能分别配置。

**9. 如果一个问题同时包含趋势和明细需求，如何处理？**

参考回答：把问题拆成趋势和明细两个子任务，通常先得到趋势或异常时间段，再将其作为明细筛选条件。两个结果通过汇总节点合并，保留各自 SQL、口径和数据引用；不能把两个需求硬塞进一条不可维护的 SQL。

**10. SQL 生成前向模型提供了哪些上下文？**

参考回答：当前提供标准化问题，以及召回后的表名、字段名、中文描述和相似字段，不把完整 Schema 全部交给模型。可信 Join、权限过滤、指标定义和枚举治理属于后续可以补齐的语义层能力。

**11. 生成 SQL 后经过哪些校验才能执行？**

参考回答：当前先做 SQL 语法校验，再检查趋势 SQL 是否具有时间粒度和聚合函数。它不能保证 SQL 业务正确。AST、表字段白名单、只读账号、行数限制、超时和 `EXPLAIN` 是明确的演进方案，面试时必须与现状分开。

**12. 如何将数据库结果衔接到后续统计分析？**

参考回答：每个计划步骤只执行一条 SQL，并创建一个 Doris 逻辑 View；View 名称写入 State，后续步骤可以引用。View 的过期时间登记在业务表中，由每日任务清理。所有步骤完成后，模型结合问题和步骤结果组织最终回复。

**13. “重点关注人员”和“疑似风险人员”是模型判断还是规则判断？**

参考回答：最终判定应由可审计的业务规则或模型服务完成，规则版本、阈值和命中原因都要记录。大模型适合理解问题、选择分析路径和解释结果，不适合临时决定高影响风险标签。

**14. 为什么业务风险判断不能完全依赖大模型？**

参考回答：大模型输出存在随机性，难以保证同输入同结果，也可能缺乏最新业务口径。风险判断要求一致、可解释、可审计和可申诉，因此核心规则必须确定化；模型只能提供辅助信息，不能成为唯一依据。

**15. FastAPI 接口采用同步还是异步？为什么？**

参考回答：HTTP 层使用异步接口，适合等待模型、数据库和缓存等 I/O；但异步不等于所有调用自动非阻塞。同步数据库驱动或 CPU 密集统计需要放到线程池、任务队列或改用异步客户端，并设置并发上限。

**16. 数据库查询是同步操作时，如何避免阻塞 FastAPI 事件循环？**

参考回答：短期可以通过受控线程池执行同步查询，线程池与其他任务隔离并限制队列；长期可使用成熟的异步驱动。无论哪种方式都要设置连接池、查询超时和取消机制，不能无限增加线程。

**17. Agent 执行时间较长时，接口如何处理超时？**

参考回答：短请求可以流式返回节点状态或最终结果；长任务改为提交任务后返回 `task_id`，由后台执行，客户端轮询或通过 SSE/WebSocket 接收更新。人工审批天然使用异步任务模式，状态由 Checkpoint 和任务表持久化。

**18. 多实例部署后，会话缓存如何共享？**

参考回答：当前历史消息随 LangGraph State 一起通过 PostgreSQL Checkpoint 持久化，没有使用 Redis 做短期会话缓存，也没有完成历史压缩。多实例可以通过同一 `thread_id` 读取共享 Checkpoint；生产化还需要补充并发版本控制和会话/Checkpoint 职责拆分。

**19. 如何保证同一会话中的并发请求不会覆盖状态？**

参考回答：对 State 使用版本号和乐观锁，写入时比较版本；同一 thread 的执行可用分布式锁或队列串行化。产品上还应为每个请求分配 task ID，明确新问题是追加、取消前一任务还是并行分析。

**20. 项目中最难解决的问题是什么？最终如何处理？**

参考回答：

> 最难的是多步骤查询如何保持同一业务口径。项目把任务计划约束为固定 JSON，服务端校验后由用户确认；每个步骤只生成一条 SQL，通过 View 名称传递依赖，并把当前步骤和重试次数写入 State。这样能够区分错误发生在问题理解、计划、SQL 还是执行阶段。

回答时应替换为自己真实处理过的问题和指标，避免编造线上结果。

**21. 你如何证明这个项目确实提升了业务查询效率？**

参考回答：项目因部门调整和业务线取消而没有上线，因此不能证明提升了线上业务效率。可以展示开发测试中的任务完成情况和错误案例，但不能使用上线用户数、人工工时下降或准确率提升等没有发生的数据。

**22. 项目上线后出现过哪些错误案例？**

参考回答：项目没有线上错误案例。开发测试中曾把 SQL 语法通过等同于结果正确，模型生成的聚合 SQL 能执行，但时间粒度与问题不一致。之后增加趋势/明细特征检查；同时明确这仍不能替代 AST、可信 Join 和结果级评测。

**23. 如果重新设计一次，你会重点改进哪些部分？**

参考回答：优先建设版本化的语义层和评测体系，把业务指标、Join 和权限从 Prompt 配置提升为可治理资产；查询执行增加成本估算和隔离；会话只保存结构化状态及结果引用。模型或框架升级排在这些基础治理之后。

**24. 项目中哪些代码是你独立负责的？**

参考回答：项目只有一名前端和一名后端，后端由我负责，包括 FastAPI 接口、LangChain 模型与 Tool 封装、LangGraph 节点和 State、PostgreSQL Checkpoint、Doris 查询衔接及 Langfuse 接入。项目未上线，数据库生产权限和上线运维不属于已完成工作。

**25. 如何区分 LangChain、LangGraph 和 Langfuse 在项目中的职责？**

参考回答：LangChain 负责模型、Prompt、结构化输出和 Tool 的基础封装；LangGraph 负责带状态的流程、条件分支、循环、Checkpoint 和人工中断；Langfuse 负责链路追踪、Prompt 版本、Token、延迟、成本和评估。三者分别对应能力组件、工作流编排和可观测性。

## 十、场景设计题

**1. 用户问“最近风险情况怎么样”，你会如何让 Agent 澄清时间范围和指标口径？**

参考回答：先检查会话是否已有时间和风险口径；没有时指出“最近”和“风险情况”均不明确，提供最少必要选项，例如“近 30 天还是本季度，关注风险人数、占比还是新增趋势”。用户确认后把选择写入结构化 State，后续轮次复用并在答案中展示口径。

**2. 用户先问趋势，随后说“把异常人员列出来”，状态如何流转？**

参考回答：第二轮识别为对上一轮结果的下钻，继承业务范围、时间和异常定义，新增明细意图。Graph 从会话加载进入明细分支，可以引用上一轮异常时间段或指标条件，重新做字段权限和 SQL 校验，返回脱敏、分页的人员列表。

**3. Schema 中有几十张表、几千个字段，如何控制 Prompt 长度？**

参考回答：先按业务域和权限过滤，再做表级混合召回、字段级重排，并沿可信关系补充少量 Join 表。设置候选数量和 Token 预算，只提供字段定义、关系及必要枚举；召回置信度不足时澄清，不把全量 DDL塞入 Prompt。

**4. SQL 执行超时，但语法正确，你会如何诊断和修复？**

参考回答：先取消数据库端查询并查看 `EXPLAIN`、扫描量、索引或分区、Join 顺序和锁等待，区分 SQL 代价与数据库负载。能安全优化时缩小时间范围、补条件、改写 SQL 或使用聚合视图；超过成本上限则提示用户调整，不进行盲目原样重试。

**5. 查询返回十万行数据，如何进行后续统计分析？**

参考回答：不把十万行送给模型。尽量把聚合、排序和筛选下推到数据库，或在受控计算节点处理；State 只保存结果集 ID、行列信息、统计摘要和少量脱敏样例，明细通过分页下载并受权限控制。

**6. 模型生成了合法 SQL，但关联条件错误，如何发现？**

参考回答：对照可信 Join 元数据检查关联键和基数，运行 `EXPLAIN` 或小范围诊断，观察 Join 前后行数是否异常膨胀，并用业务不变量校验结果。高频指标建立金标查询和回归集，不能期待语法解析器发现语义 Join 错误。

**7. 数据库字段发生变更，Agent 开始大量报错，如何快速止损？**

参考回答：监控按错误类型发现字段不存在的集中上升后，暂停受影响业务域或回退到上一版 Schema 索引，并返回可解释降级提示。随后同步新元数据、重建并验证索引、更新评测样例，再灰度恢复；Schema 版本要与 Prompt Trace 关联。

**8. 某个模型版本 SQL 正确率提高，但延迟和成本翻倍，是否上线？**

参考回答：先按业务难度分层评估收益，不直接看平均值。可以让轻量模型处理相关性和简单查询，复杂或低置信度问题升级到新模型；结合任务价值设定正确率、P95 延迟和单任务成本预算，再灰度验证。

**9. 业务人员认为结果错误，但 SQL 执行正常，如何定位问题？**

参考回答：从 Trace 还原原问题、标准化口径、Schema 版本、SQL、数据快照时间和后处理规则。依次验证需求理解、指标定义、Join、过滤、源数据和展示，和业务人员对齐期望结果；将确认后的案例加入回归集，而不是只修改当次回答。

**10. 如果要支持多个数据库和不同租户，架构需要做哪些调整？**

参考回答：引入数据源注册与方言适配层，按租户解析授权数据源、Schema 索引、语义层和只读凭据；State 中显式携带租户与数据源 ID。连接池、缓存、Checkpoint、Trace 和结果集都要租户隔离，SQL 解析、限流、超时及评测按方言配置，禁止模型自行选择任意数据源。

- 所有性能数据、准确率和线上事故只陈述真实发生过的内容。
