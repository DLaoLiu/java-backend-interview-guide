## Java、集合与并发

### 1. HashMap 放入不同 key，为什么会落到同一个位置？

::: info 事故现场
代码向 HashMap 放入大量用户对象。数据越多，查询越慢，调试时发现多个 key 落在同一个桶里。
:::

**表面现象：** key 不同，却发生哈希冲突；一个桶后面挂了多个节点。

**原因链：**

1. HashMap 先根据 key 计算 hash。
2. 再通过 `(n - 1) & hash` 定位有限的数组位置。
3. key 的数量远大于桶的数量，不同 key 落入同一个桶无法完全避免。
4. 冲突少时用链表保存；链表过长时逐个比较会变慢。
5. JDK 8 在链表长度达到 8、数组长度至少为 64 时转成红黑树。

**处理思路：** 使用稳定且分布合理的 `hashCode()`；key 参与比较的字段不要在放入 Map 后修改；预估数据量时设置合适初始容量；并发读写使用 ConcurrentHashMap。

**60 秒回答：**

> HashMap 的数组位置是有限的，不同 key 可能计算出同一个桶，这就是哈希冲突。JDK 8 使用数组加链表或红黑树处理冲突。put 时先计算 hash 和桶下标，桶为空就插入；不为空就比较 key，相同则覆盖，不同则加入链表或树。链表达到 8 且数组至少为 64 时树化，元素超过容量乘负载因子后扩容。

**记忆主线：** 算 hash → 找桶 → key 比较 → 链表冲突 → 红黑树优化 → 扩容。

### 2. HashMap 并发 put 后，为什么数据数量不对？

::: info 事故现场
两个线程同时向同一个 HashMap 写统计结果，任务结束后 Map 中的数据比预期少。
:::

**表面现象：** 没有明显异常，但部分写入被覆盖，读取也可能看到不完整状态。

**原因链：**

1. HashMap 的桶写入、链表修改和扩容没有并发保护。
2. 两个线程可能同时判断桶为空，然后后写入的节点覆盖先写入的节点。
3. 即使换成 ConcurrentHashMap，“先 get 再 put”仍是两个操作，不保证组合原子性。

**处理思路：** 使用 ConcurrentHashMap；复合操作使用 `compute`、`merge`、`putIfAbsent`；计数热点可使用 LongAdder；先确认是否真的需要多个线程共享可变 Map。

**60 秒回答：**

> HashMap 不是线程安全容器，并发 put 可能发生覆盖、丢失和扩容期间的不一致。ConcurrentHashMap 在 JDK 8 中对空桶使用 CAS，桶冲突时对桶头加锁，读操作尽量无锁。但单个方法线程安全不代表组合操作安全，因此统计更新应使用 compute、merge 等原子方法。

**记忆主线：** 容器安全不等于业务操作原子。

### 3. HashSet 中出现“看起来一样”的两个对象，为什么没有去重？

::: info 事故现场
两个 User 对象的 id 和姓名完全相同，加入 HashSet 后集合大小却是 2。
:::

**表面现象：** 业务上认为对象相同，但集合认为它们不是同一个元素。

**原因链：**

1. HashSet 底层依赖 HashMap。
2. 它先使用 `hashCode()` 找桶，再使用 `equals()` 判断桶内是否相等。
3. 只重写 equals 而没有重写 hashCode，相等对象可能进入不同桶。
4. 两个方法都没重写时，默认比较对象身份。

**处理思路：** equals 和 hashCode 使用同一组稳定字段；避免用可变字段作为 hash 依据；实体、DTO 和数据库对象的相等语义要明确。

**60 秒回答：**

> equals 相等的对象必须具有相同 hashCode，否则 HashSet 或 HashMap 可能先把它们分到不同桶，根本没有机会执行 equals。hashCode 相同不代表一定相等，因为允许哈希冲突。作为 Map key 的字段还要保持稳定。

**记忆主线：** hashCode 决定去哪找，equals 决定是不是它。

### 4. 线程池配置了最大 100 个线程，为什么始终只有 10 个在工作？

::: danger 事故现场
线程池核心线程数 10、最大线程数 100，但使用无界队列。流量升高后队列越来越长，线程数仍是 10，最终内存告警。
:::

**表面现象：** 最大线程数看起来没有生效，接口延迟持续上升。

**原因链：**

1. 任务先交给核心线程。
2. 核心线程忙时，任务先进入队列。
3. 只有队列满了，线程池才会继续创建非核心线程。
4. 无界队列不会满，因此最大线程数基本没有机会生效。
5. 任务持续堆积，最后可能 OOM。

**处理思路：** 使用有界队列；根据任务耗时和下游容量压测线程数；设置清晰拒绝策略；监控活跃线程、队列长度、等待时间和拒绝数；不同业务使用隔离线程池。

**60 秒回答：**

> ThreadPoolExecutor 的处理顺序是核心线程、任务队列、最大线程、拒绝策略。使用无界队列时，任务会一直排队，maximumPoolSize 很难生效，因此不能直接使用某些 Executors 工厂。生产中我会显式设置有界队列、线程名称、拒绝策略和监控，并根据下游容量压测参数。

**记忆主线：** 核心 → 队列 → 最大 → 拒绝。

### 5. volatile 修饰计数器后，为什么结果仍然小于预期？

::: info 事故现场
两个线程各执行一万次 `count++`，count 使用 volatile 修饰，最终结果却小于两万。
:::

**表面现象：** 每个线程都能看见新值，但自增仍然丢失。

**原因链：**

1. volatile 保证可见性和一定的有序性。
2. `count++` 实际包含读取、加一、写回三个步骤。
3. 两个线程可能读取同一个旧值，然后分别写回相同的新值。
4. 可见性不等于复合操作的原子性。

**处理思路：** 低竞争使用 AtomicLong；高竞争统计使用 LongAdder；需要保护多个变量的一致性时使用锁。

**60 秒回答：**

> volatile 只保证线程能及时看到变量变化，并限制部分指令重排，不保证 count++ 这种读改写操作原子。计数场景可以使用 AtomicLong 的 CAS；高竞争下可以用 LongAdder 分散热点；涉及多个状态一起变化时需要锁。

**记忆主线：** 看得见，不代表抢不到。

### 6. ThreadLocal 使用一段时间后，为什么线程池内存不断增长？

::: danger 事故现场
接口把用户上下文放进 ThreadLocal，但请求完成后没有清理。运行数天后，堆中出现大量无法释放的用户对象。
:::

**表面现象：** 请求已经结束，对象却仍被线程池中的线程引用。

**原因链：**

1. ThreadLocalMap 的 key 是弱引用。
2. value 仍然是强引用。
3. 线程池线程长期存活，即使 key 被回收，value 也可能继续留在线程本地 Map。
4. 下一次任务还可能读到上一个请求的脏上下文。

**处理思路：** 在 `try/finally` 中调用 `remove()`；不要保存大对象；异步任务显式传递必要上下文；线程池任务执行前后统一清理。

**60 秒回答：**

> ThreadLocal 的 key 是弱引用，但 value 是强引用。在线程池的长生命周期线程中，如果请求结束后不 remove，value 可能长期无法释放，还会造成上下文串请求。我会在 finally 中清理，并对异步任务显式传递 requestId、租户等必要字段。

**记忆主线：** 线程不死，value 不一定走；用完必须 remove。

### 7. 线上 CPU 100%，应该先改参数还是先抓现场？

::: danger 事故现场
某 Java 服务 CPU 长时间 100%，接口超时。有人建议直接重启或扩大线程池。
:::

**表面现象：** CPU 饱和，但根因可能是死循环、锁竞争、频繁 GC 或异常重试。

**原因链：**

1. 只看进程 CPU 无法定位具体代码。
2. 先用 `top` 找高 CPU 进程和线程。
3. 把线程 ID 转为十六进制，在 `jstack` 中查对应栈。
4. 若 GC 线程占用高，再结合 GC 日志和堆趋势检查对象分配与内存压力。

**处理思路：** 先保留线程栈、GC 和监控证据；必要时摘除实例止损；定位代码后再决定限流、修复循环、减少锁竞争或调整内存。不要把重启当根因修复。

**60 秒回答：**

> CPU 100% 我会先保留现场，不直接调线程数。先用 top 定位进程和线程，再将线程 ID 转成十六进制，通过 jstack 找到具体调用栈；同时检查 GC 日志，区分业务线程、锁竞争和频繁 GC。确认根因后先摘除或限流止损，再修复并回归。

**记忆主线：** 找进程 → 找线程 → 对栈 → 看 GC → 止损修复。

## Spring 与微服务

### 8. 加了事务注解，为什么同类方法调用时没有事务？

::: info 事故现场
`createOrder()` 内部直接调用本类的 `saveDetail()`，后者标记了 `@Transactional`。保存明细异常后，数据没有按预期回滚。
:::

**表面现象：** 注解存在，但事务拦截器没有执行。

**原因链：**

1. Spring 事务通常基于代理。
2. 外部对象调用 Bean 时经过代理，代理负责开启和提交事务。
3. 本类使用 `this.saveDetail()` 是目标对象内部直接调用。
4. 调用没有经过代理，因此事务注解不会生效。

**处理思路：** 优先把事务职责拆到另一个 Bean；同时检查 public 方法、异常是否被吞、回滚类型和事务管理器；不要依赖复杂的自身代理技巧掩盖职责问题。

**60 秒回答：**

> Spring 声明式事务通常依赖代理。同类内部通过 this 调用不会经过代理，因此方法上的事务拦截可能不生效。我的首选方案是按事务职责拆到另一个 Bean，并检查方法可见性、异常传播、rollbackFor 和数据源对应的事务管理器。

**记忆主线：** 事务在代理上，自调用绕过代理。

### 9. 方法抛异常了，为什么数据库仍然提交？

::: danger 事故现场
事务方法捕获异常后只记录日志，没有继续抛出。接口返回失败，但数据库中的部分修改已经提交。
:::

**表面现象：** 业务失败和事务结果不一致。

**原因链：**

1. Spring 根据方法是否正常结束以及异常类型判断回滚。
2. 异常被 catch 后吞掉，代理看到的是“正常返回”。
3. 默认情况下，部分受检异常也不会自动回滚。

**处理思路：** 无法恢复时继续抛出业务运行时异常；或显式配置 `rollbackFor`；如果捕获是为了补偿，明确设置回滚状态；远程调用不要放在长事务中。

**60 秒回答：**

> 事务是否回滚取决于异常有没有传播到事务代理以及是否匹配回滚规则。异常被捕获后不再抛出，代理会正常提交。项目中我会统一异常类型，必要时配置 rollbackFor，并避免在事务内做长时间远程调用。

**记忆主线：** 代理没看到失败，就会当成功提交。

### 10. 日志服务挂了，为什么业务接口也被拖慢？

::: danger 事故现场
log-starter 的 AOP 切面同步调用远程日志服务。日志服务延迟从 20ms 上升到 5s，所有业务接口随之超时。
:::

**表面现象：** 非核心日志依赖变成主业务的同步阻塞点。

**原因链：**

1. 切面运行在业务请求线程中。
2. 同步 Feign 调用会占用请求线程和连接。
3. 没有短超时、隔离和降级时，慢依赖会向上游扩散。
4. 简单改成异步但使用无界队列，又可能变成内存问题。

**处理思路：** 切面只采集必要字段；使用独立有界线程池或 MQ；设置短超时、失败降级和监控；审计日志与普通日志采用不同可靠性策略；敏感字段先脱敏。

**60 秒回答：**

> 日志属于横切能力，不能成为主链路强依赖。我会让切面只做轻量采集，通过隔离的有界线程池或消息队列异步发送，设置短超时和降级。普通操作日志可以有限丢弃，审计日志需要本地缓冲或补偿，并监控队列和失败量。

**记忆主线：** 轻采集、异步化、线程隔离、失败降级、分级可靠。

### 11. Feign 超时后自动重试，为什么下游压力反而翻倍？

::: danger 事故现场
下游服务已经过载，上游配置三次立即重试。一次用户请求变成多次下游调用，故障迅速扩大。
:::

**表面现象：** 重试没有提高成功率，反而造成重试风暴。

**原因链：**

1. 超时不等于请求没有执行成功。
2. 非幂等接口重试可能重复写入。
3. 下游过载时立即重试只会增加请求量。
4. 多层服务同时重试会产生乘法放大。

**处理思路：** 先配置连接、读取和整体 Deadline；只对瞬时错误和幂等操作有限重试；使用指数退避加抖动；设置重试预算；配合限流、熔断和幂等键。

**60 秒回答：**

> 重试只适合瞬时错误和幂等操作。超时可能是下游已成功但响应丢失，非幂等重试会产生重复；下游过载时立即重试还会放大流量。我会先设置合理超时，再做有限退避重试，并配合幂等、熔断和重试预算。

**记忆主线：** 先超时，后重试；先幂等，再重试。

### 12. 列表接口只有 100 条数据，为什么执行了 101 次 SQL？

::: info 事故现场
先查询 100 个用户，再循环查询每个用户的部门信息。接口耗时随着列表长度线性增长。
:::

**表面现象：** 一次主查询加 N 次关联查询，形成 N+1。

**原因链：**

1. ORM 或业务循环隐藏了真实 SQL 次数。
2. 每次查询都产生连接、网络和解析成本。
3. 数据量小时不明显，数据量增大后延迟快速上升。

**处理思路：** 使用批量 `IN` 查询后内存组装；合适时使用 Join；固定统计可预聚合；注意一对多 Join 导致主记录重复和分页错误。

**60 秒回答：**

> N+1 是先查一批主记录，再为每条记录单独查关联数据。解决方式通常是批量 IN 查询后按 key 组装，或者一次 Join。选择 Join 时要注意一对多导致结果膨胀和分页不准，我会通过 SQL 日志和 Trace 先确认真实查询次数。

**记忆主线：** 一次查主表，循环查关联，就是 N+1。

## MySQL 与 Redis

### 13. SQL 明明建了索引，为什么 EXPLAIN 仍然走全表扫描？

::: info 事故现场
查询字段有索引，但执行计划的 `type` 是 ALL。开发认为“数据库没有使用索引就是 Bug”。
:::

**表面现象：** 索引存在，不代表使用索引成本更低。

**原因链：**

1. 对索引列使用函数或发生隐式类型转换，可能无法直接定位。
2. `LIKE '%关键词'` 无法利用普通 B+Tree 前缀。
3. 联合索引跳过最左列，不能按原排序快速定位。
4. 条件选择性太低，回表成本可能比顺序扫描更高。
5. 统计信息不准确也会影响优化器判断。

**处理思路：** 查看实际 SQL 和参数类型；检查联合索引顺序、选择性和返回列；更新统计信息；用接近生产的数据验证，不能强制索引后就结束。

**60 秒回答：**

> 建了索引不代表一定使用。函数、隐式转换、前置通配、联合索引顺序和低选择性都可能让优化器选择全表扫描。我会结合 key、rows、Extra 和真实参数判断扫描与回表成本，优化后比较实际耗时和扫描量。

**记忆主线：** 能不能用看写法，值不值得用看成本。

### 14. 一个接口突然变慢，如何确认是不是慢 SQL？

::: danger 事故现场
用户画像接口 P95 从 300ms 上升到 4s。团队直接准备加索引，但尚未确认时间花在哪里。
:::

**表面现象：** 接口慢可能来自应用、数据库、锁、网络或下游，不一定是 SQL。

**原因链：**

1. 先通过 Trace 拆分各阶段耗时。
2. 如果数据库耗时高，再从慢日志取得具体 SQL、参数、频率。
3. EXPLAIN 检查扫描、索引、Join、排序和临时表。
4. 同时检查锁等待、连接池和返回数据量。

**处理思路：** 根据证据选择联合索引、SQL 改写、游标分页、批量查询、预计算或迁移到 Doris；优化后对比 P95、扫描行数和资源消耗。

**60 秒回答：**

> 我不会看到接口慢就直接加索引。先用 Trace 确认数据库占比，再通过慢日志定位 SQL 和参数，用 EXPLAIN 看扫描量、索引、Join 和 Extra，同时排查锁等待和连接池。优化后用相同数据回归，比较 P95、扫描行数和资源。

**记忆主线：** Trace 定位层 → 慢日志找 SQL → EXPLAIN 找原因 → 数据回归。

### 15. 翻到第十万页时，为什么 MySQL 越来越慢？

::: info 事故现场
接口使用 `LIMIT 1000000, 20`。虽然只返回 20 行，数据库却扫描和丢弃了前面大量数据。
:::

**表面现象：** 返回量很小，处理量却很大。

**原因链：**

1. offset 分页需要找到前面的 offset 行。
2. 如果还要回表或排序，成本进一步增加。
3. offset 越大，扫描和丢弃越多。

**处理思路：** 连续翻页使用唯一有序键游标，例如 `id > lastId`；必须跳页时先用覆盖索引查主键再回表；限制极深页；保证稳定排序。

**60 秒回答：**

> 深分页慢是因为数据库仍要扫描并丢弃 offset 之前的数据。连续翻页我会使用基于唯一有序键的游标分页；必须跳页时可以先从覆盖索引取主键，再回表查详情。分页必须带稳定排序，避免重复和漏数。

**记忆主线：** offset 是“先走过再扔掉”，游标是“从上次位置继续”。

### 16. 两个事务都修改同一批数据，为什么发生死锁？

::: danger 事故现场
事务 A 先锁用户再锁任务，事务 B 先锁任务再锁用户。两边都等待对方释放锁。
:::

**表面现象：** 数据库检测到循环等待，回滚其中一个事务。

**原因链：**

1. 两个事务各自持有资源。
2. 又请求对方已持有的资源。
3. 访问顺序不同，形成环形等待。
4. 索引不精确还可能扩大锁范围。

**处理思路：** 统一资源访问顺序；缩短事务；确保过滤条件命中索引；避免事务内远程调用；捕获死锁错误后只对幂等事务有限重试。

**60 秒回答：**

> 死锁通常是多个事务以不同顺序获取资源形成循环等待。数据库会检测并回滚一个事务。预防上我会统一访问顺序、缩短事务、通过索引减少锁范围，并避免事务内远程调用；应用只对幂等事务做有限重试。

**记忆主线：** 顺序不一致 → 互相占有 → 循环等待。

### 17. 数据库已经更新，为什么用户仍然读到缓存旧值？

::: danger 事故现场
用户名称从“张三”改成“张三丰”，数据库更新成功，但 Redis 仍保存“张三”。
:::

**表面现象：** 数据库和缓存短暂不一致。

**原因链：**

1. 如果先删缓存再更新数据库，并发读可能把旧数据库值重新写回缓存。
2. 通常应先更新数据库，成功后删除缓存。
3. 但删除缓存也可能失败，因此 Cache Aside 仍是最终一致。

**处理思路：** 读时缓存未命中再回源；写时先数据库后删除缓存；删除失败通过重试、消息或 binlog 订阅补偿；设置 TTL；强一致场景直接读事实源。

**60 秒回答：**

> 我通常使用 Cache Aside：读时先缓存，未命中查数据库并回填；写时先更新数据库，再删除缓存。删除而不是更新能避免复杂计算和并发旧值覆盖。删除失败还要通过重试、消息或 binlog 补偿，所以它保证的是最终一致，不是强一致。

**记忆主线：** 读缓存后数据库；写数据库后删缓存；失败要补偿。

### 18. 缓存穿透、击穿、雪崩怎么从现象区分？

::: danger 事故现场
三个系统都出现数据库流量激增：A 请求的 key 永远不存在；B 是一个热点 key 刚好过期；C 是大量 key 同时过期。
:::

**表面现象：** 都是缓存未命中，但原因和治理不同。

**原因链与方案：**

- **穿透：** 数据本来不存在。使用参数校验、空值缓存、布隆过滤器。
- **击穿：** 单个热点失效。使用互斥重建、逻辑过期、热点预热。
- **雪崩：** 大量 key 同时失效或 Redis 故障。打散过期时间、多级缓存、限流降级、高可用。

**60 秒回答：**

> 穿透是查询不存在的数据，击穿是单个热点 key 失效，雪崩是大量 key 同时失效或缓存整体故障。三者都会让请求回源，但分别通过空值或布隆过滤、热点互斥重建、过期打散和限流高可用处理。

**记忆主线：** 不存在是穿透，一个热点是击穿，一大片失效是雪崩。

### 19. Redis 锁已经过期，旧任务为什么删掉了新任务的锁？

::: danger 事故现场
任务 A 获取锁后执行过久，锁自动过期；任务 B 获得同名锁。任务 A 结束时直接 DEL，误删了任务 B 的锁。
:::

**表面现象：** 锁存在，但互斥保护失效。

**原因链：**

1. 锁 value 没有标识持有者。
2. 解锁没有验证当前锁属于谁。
3. 判断和删除如果分两条命令执行，也不是原子操作。

**处理思路：** `SET key uniqueValue NX PX ttl`；使用 Lua 原子比较 value 后删除；长任务受控续期；数据库唯一约束或状态机继续兜底。

**60 秒回答：**

> Redis 锁要使用唯一 value 标识持有者，释放时通过 Lua 原子判断 value 再删除，避免旧任务误删新锁。任务可能超过租期时需要续期。但分布式锁不是最终数据正确性的唯一保障，关键业务仍需要唯一约束或状态机。

**记忆主线：** 加锁带身份证，解锁先验身份证。

### 20. Redis 内存和网络突然升高，如何判断大 key 还是热 key？

::: danger 事故现场
一个 Redis 节点延迟升高。监控发现单个 Hash 有百万成员，同时某个配置 key 每秒被读取数十万次。
:::

**表面现象：** 大 key 主要伤害传输、删除、持久化和迁移；热 key 主要造成单点 CPU 或网络热点。

**处理思路：** 使用扫描和监控识别 key 大小与访问频率；大 key 拆分、限制成员、异步删除；热 key 使用本地缓存、读副本、热点隔离或拆分；治理前先确认业务一致性要求。

**60 秒回答：**

> 大 key 是单个 value 或成员数量过大，会影响传输、删除和持久化；热 key 是访问集中，容易打满单节点 CPU 或网络。我会分别监控大小和访问频率，再通过拆分、异步删除、本地缓存、读副本或热点隔离治理。

**记忆主线：** 大 key 是“东西太多”，热 key 是“人来太多”。

## Kafka、Flink 与 Doris

### 21. Kafka 消费成功后服务宕机，为什么消息又处理了一次？

::: danger 事故现场
消费者已写入数据库，但还没提交 offset 就宕机。重启后从旧 offset 继续消费，同一条消息再次到达。
:::

**表面现象：** Kafka 的至少一次投递产生重复业务操作。

**原因链：**

1. 业务处理和 offset 提交不是同一个原子动作。
2. 处理成功、提交前故障，恢复后必然重新读取。
3. 仅依赖 Kafka 配置无法保证所有外部业务结果恰好一次。

**处理思路：** 使用业务唯一键、数据库唯一约束、状态机或去重表实现消费者幂等；成功处理后提交 offset；失败进入重试或补偿。

**60 秒回答：**

> 消费成功但 offset 未提交就宕机会导致重复消费。因此端到端可靠性不能只依赖 Kafka，消费者必须根据业务唯一键做幂等，例如唯一约束、状态机或去重表。消息处理成功后再提交 offset，失败进入重试和补偿。

**记忆主线：** Kafka 可以重放，业务必须幂等。

### 22. Kafka Lag 持续增加，应该直接扩消费者吗？

::: danger 事故现场
消费积压越来越多，团队准备把消费者从 10 台扩到 50 台，但 Topic 只有 12 个分区。
:::

**表面现象：** 消费者数量超过分区数后，新增实例会空闲。

**原因链：**

1. 同一消费组内，一个分区同一时刻只分给一个消费者。
2. 有效并行度不超过分区数。
3. 真正瓶颈也可能是慢 SQL、外部接口、单个热点分区或异常重试。

**处理思路：** 比较生产速率、消费速率和各分区 Lag；定位慢下游与热点 key；批量消费或优化 I/O；必要时评估扩分区，但注意 key 顺序和分区映射变化。

**60 秒回答：**

> 消息积压不能只靠加消费者。同组并行度不超过分区数，我会先看生产消费速率、分区 Lag 和下游耗时，区分消费者故障、慢 SQL 和分区热点。优化下游后再决定扩消费者或分区，并评估顺序性影响。

**记忆主线：** 先看速率和分区，再看下游瓶颈。

### 23. Flink 开了 Checkpoint，为什么写入结果仍可能重复？

::: danger 事故现场
Flink 从 Checkpoint 恢复后重新读取了一段 Kafka 数据，Doris 中出现重复记录。
:::

**表面现象：** 状态恢复一致，不代表外部 Sink 自动恰好一次。

**原因链：**

1. Checkpoint 保存 Flink 状态和 Source 位置。
2. 故障恢复后，Checkpoint 之后的数据会重放。
3. Sink 如果不支持事务提交或幂等写入，重放就可能产生重复。

**处理思路：** Source 必须可重放；Checkpoint 配置正确；Sink 使用事务、业务唯一键、主键模型、版本或幂等批次标识；通过对账验证端到端结果。

**60 秒回答：**

> Checkpoint 主要保证 Flink 状态一致恢复。端到端 Exactly-once 还要求 Source 可重放，Sink 支持事务提交或幂等写入。只开启 Checkpoint，无法自动保证 Doris 等外部系统没有重复。

**记忆主线：** Checkpoint 管状态，端到端还要看 Source 和 Sink。

### 24. Flink 出现反压，为什么不能只提高并行度？

::: danger 事故现场
Flink Web UI 显示上游反压。团队提高所有算子并行度后，Doris 写入压力更大，任务仍然不稳定。
:::

**表面现象：** 上游慢只是传播结果，真正瓶颈通常在某个下游算子或外部系统。

**原因链：**

1. 下游处理不过来，输出缓冲被占满。
2. 压力逐级传到上游。
3. 全部扩容可能只是更快地把流量打向已经过载的 Sink。

**处理思路：** 从 Web UI 找反压起点；检查慢算子、外部 I/O、数据倾斜、GC 和状态；优化批量写入或异步 I/O；确认 Doris 容量后再调整局部并行度。

**60 秒回答：**

> 反压表示下游速度跟不上，压力向上游传播。我会先在 Web UI 找到反压起点，再检查慢算子、外部 I/O、数据倾斜、GC 和状态大小。只有确认瓶颈可并行扩展且下游有容量时才提高并行度。

**记忆主线：** 反压显示在上游，根因通常在下游。

### 25. Doris 查询突然变慢，为什么不能照搬 MySQL 的加索引思路？

::: danger 事故现场
原本 2 秒的多维统计变成 20 秒。查询扫描数亿行，并且没有命中分区裁剪和物化视图。
:::

**表面现象：** 分析型数据库的瓶颈通常是扫描、分布、聚合和并发，不只是单行索引定位。

**原因链：**

1. 时间条件没有命中分区，扫描范围扩大。
2. 分桶不均或 Join key 倾斜，部分节点成为长尾。
3. 聚合未预计算，或者物化视图未命中。
4. 并发、导入和小文件也可能争抢资源。

**处理思路：** 查看 Query Profile；检查分区裁剪、扫描量、谓词下推、Join 分布、数据倾斜和物化视图；稳定高频查询使用预计算，探索查询保留明细能力。

**60 秒回答：**

> Doris 面向大范围分析，慢查询重点看分区裁剪、扫描量、谓词和聚合下推、Join 分布、数据倾斜、物化视图以及集群并发。我会先用 Query Profile 找长耗时阶段，再调整分区分桶或预计算，而不是直接套 MySQL 加索引。

**记忆主线：** 少扫描、均分布、早过滤、预聚合。
