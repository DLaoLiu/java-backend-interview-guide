# Chat-BFI Agent 事故分析题

这 15 个场景覆盖 Chat-BFI 最容易被追问的工程问题。重点不是背 LangGraph 名词，而是解释一次请求为什么会走错、卡住或产生风险。

::: tip 使用方法
先画出最小链路：问题 → 意图 → Schema → SQL → 校验 → 执行 → 分析。每个事故都在这条链路上定位。
:::

## 问题理解与 Schema

### 1. 用户问“最近风险情况怎么样”，Agent 为什么不能直接生成 SQL？

::: info 事故现场
Agent 把“最近”理解为 7 天，把“风险情况”理解为风险人数。业务人员实际想看本季度风险占比。
:::

**表面现象：** SQL 可以执行，但问题理解从第一步就错了。

**原因链：**

1. “最近”没有明确时间范围。
2. “风险情况”可能指人数、占比、新增或趋势。
3. 模型自行补全口径，后续 SQL 越正确，最终答案反而越确定地错误。

**处理思路：** 先读取会话中是否已有口径；没有时只澄清会影响结果的最少信息；将时间、指标、维度和筛选条件写入结构化 State；最终答案展示口径。

**60 秒回答：**

> Text2SQL 的第一风险不是语法，而是问题理解。遇到“最近”“风险情况”这类歧义，我不会让模型直接猜，而是先抽取指标、维度、时间和筛选条件，缺少关键口径时发起最小澄清。确认结果进入结构化 State，后续 SQL 和解释都使用同一口径。

**记忆主线：** 先把问题说清，再让 SQL 写对。

### 2. 数据库有几千个字段，为什么把完整 DDL 给模型后效果更差？

::: danger 事故现场
为了避免漏表，系统把全库 DDL 放进 Prompt。Token、延迟和成本增加，模型还经常选错同名字段。
:::

**表面现象：** 信息更多，却产生更大干扰。

**原因链：**

1. 大量无关 Schema 占用上下文。
2. 多表存在 `status`、`create_time` 等同名字段。
3. 模型可能凭名称猜 Join，而不是使用可信关系。
4. 未授权字段也可能被带入上下文。

**处理思路：** 先按租户、用户和业务域过滤；使用关键词加向量混合召回表和字段；沿可信关系补充必要 Join 表；限制候选数量；置信度不足时澄清。

**60 秒回答：**

> Schema Linking 不是把完整 DDL 交给模型，而是根据问题召回相关表、字段和 Join。生产中我会先做权限和业务域过滤，再混合检索和重排，只提供必要注释、枚举及可信关系。这样同时降低 Token、选错字段和越权风险。

**记忆主线：** 先过滤权限，再召回相关，最后补关系。

### 3. 两张表都有 status 字段，Agent 为什么选错了？

::: info 事故现场
问题询问“任务状态”，模型却使用了用户状态字段。SQL 语法和字段都合法，结果完全不符合业务。
:::

**表面现象：** 技术字段同名，业务语义不同。

**原因链：**

1. 只检索字段名，没有字段注释和所属实体。
2. 缺少状态枚举说明。
3. 问题中的“任务”没有用于重排候选。

**处理思路：** Schema 文档包含完整限定名、中文含义、业务域、枚举和数据粒度；结合问题实体重排；高频业务术语维护显式映射。

**60 秒回答：**

> 同名字段不能只按名称匹配。我会把表的业务域、字段注释、枚举、数据粒度和实体关系一起作为 Schema 元数据。对“重点人员”“任务状态”等业务词维护术语映射，避免让模型临时猜字段含义。

**记忆主线：** 字段名只是线索，业务实体才决定含义。

## SQL 生成、校验与执行

### 4. SQL 报“字段不存在”，Agent 应该无限重试吗？

::: danger 事故现场
模型生成不存在的字段，数据库报错。Agent 连续生成三次几乎相同的 SQL，延迟和 Token 持续增加。
:::

**表面现象：** ReAct 进入无效循环。

**原因链：**

1. 错误没有被标准化，只把完整堆栈重新交给模型。
2. State 没有记录已尝试 SQL 和错误。
3. 没有最大迭代次数和重复指纹检测。

**处理思路：** 提取错误类型、位置和相关 Schema；保存 SQL 规范化指纹；每次重试重新做安全校验；相同错误或超过次数后终止并转人工或提示用户。

**60 秒回答：**

> SQL 错误自修复必须有边界。我会把脱敏后的错误类型、原 SQL、相关 Schema 和历史尝试反馈给生成节点，并记录 SQL 指纹和重试次数。新 SQL 仍要经过全部安全校验；连续相同错误或达到阈值后终止，不能无限 ReAct。

**记忆主线：** 错误要分类，重试要留痕，循环要有上限。

### 5. SQL 执行成功，为什么“人数”统计翻了三倍？

::: danger 事故现场
人员表与行为表是一对多关系。模型 Join 后使用 `COUNT(*)`，一个人有三条行为就被统计三次。
:::

**表面现象：** SQL 语法正确、执行成功，但业务结果错误。

**原因链：**

1. “人数”的业务口径应按人员主键去重。
2. 一对多 Join 放大了行数。
3. 只看执行成功率无法发现语义错误。

**处理思路：** 语义层定义“人数”等指标；Schema 关系记录基数；结果守卫比较 Join 前后行数；使用 `COUNT(DISTINCT person_id)` 或先聚合再 Join；加入金标评测。

**60 秒回答：**

> Text2SQL 最难的是 SQL 能执行但业务语义错误。一对多 Join 后使用 COUNT(*) 会把人数放大。我会在语义层明确指标口径，记录 Join 基数，执行后检查行数异常，并用结果正确率而不是只用执行成功率评估。

**记忆主线：** 能运行不等于算得对；人数先看是否去重。

### 6. 模型只生成 SELECT，为什么仍可能不安全？

::: danger 事故现场
一条 SELECT 查询了全量身份证和手机号，扫描数亿行并拖慢数据库。
:::

**表面现象：** 只读不等于低风险。

**原因链：**

1. SELECT 仍可能越权读取敏感字段。
2. 缺少租户条件可能产生跨租户数据泄露。
3. 全表扫描和笛卡尔积可能耗尽数据库资源。
4. 大量结果进入模型和 Trace 会二次泄露。

**处理思路：** 只读账号只是最后防线；AST 校验表字段白名单、租户条件、危险函数、Join 和 Limit；设置语句超时和最大行数；结果进入模型前脱敏截断。

**60 秒回答：**

> SQL 安全不只是拦截 DELETE。SELECT 也可能越权、泄露敏感字段或拖垮数据库。我的防线包括权限过滤后的 Schema、AST 白名单、租户条件、Limit、超时、只读账号和结果脱敏，并对高成本查询使用 EXPLAIN 或风险审批。

**记忆主线：** 生成前限 Schema，执行前查 AST，数据库用只读，结果再脱敏。

### 7. 查询返回十万行，为什么不能全部放进 State 再交给模型？

::: danger 事故现场
明细查询返回十万行，Checkpoint 写入变慢，Prompt 超长，敏感数据还进入了 Langfuse。
:::

**表面现象：** 状态膨胀、成本上升、恢复变慢并扩大数据风险。

**原因链：**

1. LangGraph State 可能被序列化和持久化。
2. 大结果反复在节点间复制。
3. 模型无法可靠处理任意大表。
4. Trace 记录扩大泄露面。

**处理思路：** 聚合、过滤和排序尽量下推数据库；结果保存在受控缓存或对象存储；State 只放结果集 ID、Schema、行数、统计摘要和脱敏样例；明细分页查看。

**60 秒回答：**

> 大结果集不应该直接进入 LangGraph State。它会增加 Checkpoint、序列化、Token 和隐私风险。我会让 SQL 先完成必要聚合，大结果保存到受控存储，State 只保留结果集引用、结构、行数和统计摘要。

**记忆主线：** 数据放存储，状态放引用，模型看摘要。

## LangGraph、会话与人工确认

### 8. Agent 为什么在查询工具和修复工具之间来回循环？

::: danger 事故现场
模型重复调用同一个工具，参数几乎不变。Graph 迟迟不能到达结束节点。
:::

**表面现象：** 图中有循环，但没有业务终止条件。

**原因链：**

1. 只依赖模型决定是否结束。
2. State 没有迭代次数、调用历史和错误指纹。
3. Tool 前置条件不明确。

**处理思路：** 设置图级递归上限和业务最大迭代；记录 Tool 名、参数指纹和 Observation；重复调用直接终止；安全拒绝不得进入绕过式重试。

**60 秒回答：**

> LangGraph 允许循环，但终止条件必须由代码控制。State 中记录迭代次数、工具调用和错误指纹；正常成功、问题无关、人工拒绝或超过阈值都进入明确结束节点。模型负责语义选择，代码负责安全和循环上限。

**记忆主线：** 模型决定下一步，代码决定能走几步。

### 9. 服务重启后，等待审批的 Agent 为什么找不到原状态？

::: danger 事故现场
高风险 SQL 等待人工确认时服务发布重启。内存中的 State 丢失，审批通过后无法继续执行。
:::

**表面现象：** Human-in-the-Loop 只有暂停，没有持久化恢复。

**原因链：**

1. State 只保存在进程内存。
2. 没有持久化 Checkpointer。
3. 审批单和图执行缺少统一 threadId、审批 ID 和 SQL 版本。

**处理思路：** 中断前持久化 Checkpoint；审批业务数据进入数据库；通过 threadId 关联；恢复时验证审批状态和 SQL 哈希；有副作用节点使用幂等键。

**60 秒回答：**

> Human-in-the-Loop 需要持久化 Checkpoint。审批前保存图状态，审批单独进入业务数据库，通过 threadId 和审批 ID 关联。人工确认后恢复执行时还要验证待执行 SQL 的哈希，避免审批内容被替换。

**记忆主线：** 中断前存状态，恢复时验版本。

### 10. 用户批准了一条 SQL，为什么执行前仍要重新校验？

::: danger 事故现场
审批页面显示的是 SQL A，但等待期间 State 被后续请求更新成 SQL B。系统直接执行了当前 State 中的 SQL。
:::

**表面现象：** 人工批准对象和最终执行对象不一致。

**原因链：**

1. 审批没有绑定 SQL 版本或哈希。
2. 同一会话并发请求覆盖状态。
3. 人工确认被误认为可以替代安全校验。

**处理思路：** 审批单保存不可变 SQL、风险和影响范围；执行时比较哈希和状态版本；重新做 AST、权限和超时校验；同一 thread 使用版本控制或串行化。

**60 秒回答：**

> 人工确认不是绕过安全策略。审批必须绑定具体 SQL 版本和哈希，恢复执行时先验证内容未变化，再重新执行 AST、权限和成本校验。并发会话还要使用版本号或串行任务防止 State 覆盖。

**记忆主线：** 人批的是哪一版，系统只能执行哪一版。

### 11. 多轮对话一直追加历史，为什么回答越来越慢、越来越偏？

::: danger 事故现场
系统把全部历史消息、SQL 和结果放进每次 Prompt。十几轮后 Token 大幅增长，早期错误口径还影响新问题。
:::

**表面现象：** 上下文无限扩张并产生历史污染。

**原因链：**

1. 并非所有历史都与当前问题相关。
2. 自然语言回答会丢失原始结构和口径。
3. 旧 Schema、SQL 和错误结论可能被继续继承。

**处理思路：** 保留最近窗口；旧消息滚动摘要；指标、时间、筛选条件和结果引用使用结构化业务状态；每轮重新执行权限与 Schema Linking；话题切换时创建新任务上下文。

**60 秒回答：**

> 会话记忆不能等于把全部历史塞进 Prompt。我会区分最近消息、历史摘要和结构化业务状态，只继承明确的指标、时间、筛选条件及结果引用。每轮重新做权限和 Schema Linking，话题切换时隔离任务上下文。

**记忆主线：** 消息做窗口，历史做摘要，业务事实做状态。

### 12. 用户先看趋势，再说“把异常人员列出来”，Graph 怎么走？

::: info 事故现场
第二轮只有一句“把异常人员列出来”，没有重复时间和异常定义。
:::

**表面现象：** 当前问题不完整，但它是对上一轮趋势结果的下钻。

**原因链：**

1. 需要识别“异常人员”指向上一轮异常时段或规则。
2. 继承业务范围和时间，但查询类型从趋势变成明细。
3. 明细字段涉及更严格权限和脱敏。

**处理思路：** 加载上一轮结构化意图和结果引用；识别延续关系；继承必要槽位；进入明细分支；重新进行字段权限、SQL 校验和行数限制。

**60 秒回答：**

> 第二轮会先判断是新话题还是对上一轮下钻。确认延续后继承上一轮的业务范围、时间和异常定义，把 queryType 改为明细，再重新执行 Schema Linking、字段权限和 SQL 校验。不能直接复用上一轮自然语言回答。

**记忆主线：** 继承条件，不继承旧 SQL；趋势转明细，权限重新查。

## 观测、评估与业务规则

### 13. Agent 很慢，如何判断是模型、SQL 还是循环导致？

::: danger 事故现场
一次请求耗时 40 秒。普通接口日志只记录了开始和结束，无法知道时间花在哪里。
:::

**表面现象：** Agent 由多个模型、Tool 和节点组成，单条耗时没有诊断价值。

**原因链：**

1. 模型可能输入过长或多次重试。
2. Schema 检索或 SQL 可能慢。
3. Graph 可能产生无效循环。
4. 人工等待不应与计算耗时混在一起。

**处理思路：** Langfuse 中一次任务为 Trace；节点为 Span；模型调用为 Generation；记录模型/Prompt 版本、Token、首 Token、总延迟、Tool 耗时、重试和最终状态。

**60 秒回答：**

> 我会用 Langfuse 把一次用户任务作为 Trace，各 LangGraph 节点作为 Span，模型调用作为 Generation。通过节点耗时、Token、工具调用和重试次数，区分模型生成、Schema 检索、SQL 执行和循环问题。敏感 SQL 和结果只记录哈希、摘要或脱敏内容。

**记忆主线：** Trace 看全程，Span 看节点，Generation 看模型。

### 14. SQL 执行成功率达到 95%，为什么业务仍认为系统不好用？

::: danger 事故现场
大多数 SQL 能运行，但用户发现时间口径、人数去重和风险定义经常错误。
:::

**表面现象：** 技术执行成功不等于完成用户任务。

**原因链：**

1. SQL 可能选错表、字段、Join 或业务指标。
2. 结果正确但解释可能错误。
3. 歧义问题本应澄清，却被强行生成 SQL。

**处理思路：** 分层评估 Schema Recall、SQL 执行正确率、结果正确率和任务完成率；加入安全攻击、歧义、多轮和空结果样例；在线关注人工介入、迭代、延迟和用户反馈。

**60 秒回答：**

> Text2SQL 不能只看执行成功率。SQL 能运行但结果可能错误。我会分别评估 Schema 召回、执行正确率、结果正确率和任务完成率，并使用真实问题构建带业务口径的评测集。最终核心指标是用户任务是否正确完成。

**记忆主线：** 能执行是底线，结果正确才有用，任务完成才有价值。

### 15. “疑似风险人员”为什么不能让大模型直接决定？

::: danger 事故现场
同一份数据多次调用模型，风险名单略有不同，且无法给出稳定规则供业务申诉。
:::

**表面现象：** 高影响业务判断缺乏一致性、审计和可复现性。

**原因链：**

1. 大模型输出存在随机性。
2. Prompt 可能遗漏最新业务阈值。
3. 纯自然语言判断无法稳定回放和申诉。

**处理思路：** 风险规则由代码、SQL 或受治理的模型服务执行；记录规则版本、阈值、输入和命中原因；大模型负责理解问题和解释证据；高风险结果进入人工确认。

**60 秒回答：**

> 风险人员属于高影响判断，必须一致、可解释、可审计。核心判定应由版本化业务规则或受治理的模型服务完成，记录阈值和命中原因。大模型可以理解问题和生成解释，但不应临时发明风险标准或成为唯一决策者。

**记忆主线：** 模型负责理解和解释，规则负责最终判定。

## Chat-BFI 故障定位总图

```text
回答不对
  ├─ 问题是否理解错？       → 指标、维度、时间、筛选
  ├─ Schema 是否链接错？    → 表、字段、Join、业务术语
  ├─ SQL 是否语义错？       → 聚合、去重、时间、租户
  ├─ 执行是否有风险？       → AST、权限、Limit、超时
  ├─ 后处理是否算错？       → 统计规则、风险规则、版本
  └─ 解释是否脱离证据？     → 结果摘要、引用、截断状态
```
